# 统一文件上传服务 · 设计

> 版本 v1.0（2026-07-24）· 波次 1 前置地基
> 背景：7/18 评审会多处需要附件/图片/文件（工单附件、工单图片、平面图、合同上传、CAD、巡检图片、资料归档）。核实项目**当前无任何文件上传能力**（后端零 MultipartFile / 无上传接口 / 无附件表 / 无静态资源映射；前端零 el-upload），需从零建一套统一服务。
> 已确认：存储方式 = **本地磁盘**。

## 1. 目标与非目标

**目标**：提供一套通用的文件上传/下载/删除/列表能力，供所有业务模块复用；提供一个可复用的前端上传组件。

**非目标**：
- 不在本次把上传接进具体业务页面（工单/合同/巡检等各自后续接入）。
- 不做对象存储（OSS/MinIO），本地磁盘即可；但目录路径通过配置项暴露，未来可替换。
- 不做在线解析/预览引擎（CAD/OCR），那是后续独立工作。

## 2. 架构

- 新增后端模块 `com.zhyq.park.file`，包结构遵循项目规范 `{entity,mapper,controller}`，存储逻辑因涉及磁盘 IO 与安全校验，单列一个 `FileStorageService`。
- 存储：文件落本地磁盘 `${zhyq.upload.path}`（默认 `./uploads`），按 `yyyy/MM/` 分目录。文件名用 UUID + 原扩展名。
- 一张**通用附件表** `sys_file`，靠 `biz_type + biz_id` 关联任意业务对象；不给各业务表加附件字段。

## 3. 数据模型：sys_file（Flyway V28）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | 主键 |
| biz_type | VARCHAR(32) | 业务类型：work_order/contract/patrol/building_doc… 可空 |
| biz_id | BIGINT | 关联业务主键，可空（先传后关联） |
| original_name | VARCHAR(255) | 原始文件名 |
| store_path | VARCHAR(512) | 相对存储路径 yyyy/MM/uuid.ext |
| url | VARCHAR(512) | 访问 URL |
| file_size | BIGINT | 字节数 |
| content_type | VARCHAR(128) | MIME |
| ext | VARCHAR(32) | 扩展名 |
| + BaseEntity | | tenant_id/create_by/create_time/update_by/update_time/version/deleted |

索引：`idx_biz (biz_type, biz_id)`。

## 4. 接口（/file 前缀，统一 Result 返回）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | /file/upload | 单文件，MultipartFile + 可选 bizType/bizId，返回附件记录（含 url） |
| POST | /file/upload-batch | 批量上传，返回记录列表 |
| GET | /file/list?bizType=&bizId= | 查某业务对象的附件列表 |
| DELETE | /file/{id} | 逻辑删除记录 + 删磁盘文件 |

静态访问：`WebConfig` 增加资源映射 `/uploads/**` → `${zhyq.upload.path}`。

## 5. 安全与校验（必做）

1. **类型白名单**：允许 jpg/jpeg/png/gif/webp/pdf/doc/docx/xls/xlsx/ppt/pptx/dwg/dxf/txt/zip；拒绝可执行（exe/jsp/sh/bat/…）。
2. **大小限制**：application.yml `max-file-size: 20MB`、`max-request-size: 50MB`；后端二次校验。
3. **路径穿越防护**：不信任原文件名，一律 UUID 重命名；校验最终规范化路径必须落在上传根目录内。
4. **扩展名 + content-type 双校验**，不一致或不在白名单则拒绝。

## 6. 配置（application.yml）

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 20MB
      max-request-size: 50MB
zhyq:
  upload:
    path: ./uploads        # Docker 挂卷持久化
    url-prefix: /uploads
```

Docker：`docker-compose.full.yml` 后端服务挂载卷持久化 `./uploads`（DEPLOY.md 补一句）。

## 7. 前端

- `src/api/file.js`：封装 `upload / uploadBatch / list / remove`，走统一 `@/utils/request`。
- `src/components/FileUpload.vue`：包 `el-upload` 的可复用组件，支持多文件、图片预览、上传进度、删除；`v-model` 绑定附件列表。业务页面直接引用，不重复写上传逻辑。

## 8. 多园区

`sys_file` 含 `tenant_id`（BaseEntity 自带）。波次 0 多园区落地时自然纳入隔离，本次不特殊处理。

## 9. 测试

对纯逻辑写 JUnit 单测（项目安全/关键逻辑补测试约定）：
- 文件名生成：UUID + 保留原扩展名。
- 路径穿越防护：`../` 等恶意名被规范化拦截。
- 类型白名单：允许/拒绝判断。

## 10. 硬约束遵循

- 新增 entity/controller/mapper 类名先查重（避免跨包重名导致 bean 冲突）：`SysFile` / `SysFileMapper` / `FileController` / `FileStorageService` 需确认不重名。
- 不改 common 基座、application.yml 现有段之外的内容仅新增。
- `mvn` 在 backend/ 跑，编译验证。

## 11. 交付验收

- 后端：上传返回 url，磁盘生成文件；list/delete 正常；恶意类型/超大文件被拒；单测通过；`mvn compile` 通过。
- 前端：FileUpload 组件能选文件、显进度、传成功回填 url、删除；build 通过。
- 不接入具体业务页面（后续各功能接入）。
