# ver4.2 超级管理员用户与权限管理 · 设计

> 基线：`ver4.1` / `9f0fd64`  
> 目标版本：`ver4.2`  
> 已确认方案：用户可选择多个角色，权限由角色继承；角色管理同时提供权限配置。

## 1. 目标

超级管理员登录后可以在系统页面内完成以下操作，不再登录服务器手工修改数据库：

1. 新建和编辑用户，并为用户选择一个或多个启用角色。
2. 为普通角色配置菜单和按钮权限。
3. 为用户选择 `admin` 角色，从而创建新的超级管理员。
4. 查看用户当前角色并重新分配。
5. 安全保护现有超级管理员，避免系统失去全部管理员。

## 2. 非目标

- 不新增用户级独立权限表，不支持“角色权限之外再单独加减权限”。
- 不在本版本重做全部前端路由和菜单体系；角色配置作用于现有 `@PreAuthorize` 权限点，JWT 仍在登录时载入权限。
- 不改变现有密码算法、JWT 格式、多租户模型和数据范围语义。
- 不删除或重建线上已有用户、角色和关联数据。

## 3. 权限模型

沿用现有数据链路：

```text
sys_user
  -> sys_user_role
  -> sys_role
  -> sys_role_menu
  -> sys_menu.perm
  -> AuthQueryMapper
  -> JWT auth claim
```

- 一个用户可以绑定多个角色。
- 一个角色可以绑定多个菜单或按钮权限。
- 多角色权限取并集，登录时去重后写入 JWT。
- 权限或角色变更后，被修改用户需重新登录，最长受当前 JWT 有效期约束。
- `admin` 是受保护的超级管理员角色编码；拥有该角色的启用用户视为有效超级管理员。

## 4. 后端设计

### 4.1 用户管理

新增 `SysUserSaveRequest`，明确接收用户字段与 `roleIds`，避免直接把数据库实体作为写接口输入。

新增 `SysUserDetailResponse`：

- `user`：用户基本资料，密码继续保持 WRITE_ONLY。
- `roleIds`：当前用户角色 ID 列表。

用户分页返回记录增加非持久化的 `roleNames`，由 Mapper 对当前页用户一次批量聚合查询，避免逐用户查询造成 N+1。

新增 `UserManagementService`，通过事务完成：

- 新增用户、BCrypt 密码加密、写入 `sys_user_role`。
- 修改用户资料、可选重置密码、整体替换角色关系。
- 删除用户并清理用户角色关系。
- 校验用户名唯一、角色存在且启用、角色 ID 去重。

### 4.2 角色与权限管理

新增 `RoleManagementService`，通过事务完成：

- 新增、修改和删除角色。
- 查询角色当前 `menuIds`。
- 整体替换普通角色的 `sys_role_menu` 关系。
- 校验角色编码唯一、菜单权限存在且启用、ID 去重。

新增接口：

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/system/user/{id}` | `system:user:query` | 返回用户资料与角色 ID |
| POST | `/system/user` | `system:user:add` + `system:user:role` | 新建用户并绑定角色 |
| PUT | `/system/user` | `system:user:edit` + `system:user:role` | 修改用户并替换角色 |
| DELETE | `/system/user/{id}` | `system:user:delete` | 删除用户并清理角色 |
| GET | `/system/role/{id}/menu-ids` | `system:role:query` | 查询角色权限 |
| PUT | `/system/role/{id}/menu-ids` | `system:role:permission` | 保存角色权限 |

V31 新增并自动授予 `admin` 角色两个权限点：

- `system:user:role`
- `system:role:permission`

### 4.3 关联表

新增轻量实体和 Mapper：

- `SysUserRole` / `SysUserRoleMapper`
- `SysRoleMenu` / `SysRoleMenuMapper`

两类关联表只包含自身主键和两个关联 ID，不继承 `BaseEntity`。

## 5. 超级管理员安全规则

1. 只有当前 JWT 含 `ROLE_admin` 的操作者可以给用户授予或撤销 `admin` 角色。
2. `admin` 角色不可删除、停用、修改角色编码或清空权限。
3. 删除、停用或撤销用户的 `admin` 角色前，必须保证操作后仍至少存在一个启用的超级管理员。
4. 前端对 `admin` 角色显示“系统保护”标记，禁用其编辑、删除和权限配置入口；后端仍进行强制校验，不能只依赖前端。
5. 普通角色可以被拥有相应权限的管理员配置；即使将角色管理权限授予普通用户，也不能绕过 `admin` 角色保护。

## 6. 数据库迁移

新增 `V31__rbac_management.sql`：

1. 清理 `sys_user_role(user_id, role_id)` 的历史重复行。
2. 清理 `sys_role_menu(role_id, menu_id)` 的历史重复行。
3. 增加两组唯一索引，防止并发或手工操作再次产生重复关联。
4. 插入两个新增权限点并授予 `admin` 角色，SQL 保持幂等。

迁移不修改现有用户和角色归属，因此线上已有两个超级管理员会被完整保留。

## 7. 前端设计

### 7.1 用户管理

`User.vue` 新增：

- 角色列，以标签展示当前角色名称。
- 新增/编辑弹窗中的角色多选框，只展示启用角色。
- 编辑时调用用户详情接口取得准确的 `roleIds`，不依赖列表行缓存。
- `admin` 角色在选项中标注“超级管理员”。
- 角色至少选择一个；新增时密码仍至少 6 位，编辑时密码可留空。

### 7.2 角色管理

`Role.vue` 新增“配置权限”操作和权限树弹窗：

- 权限树数据来自现有菜单列表。
- 同时展示目录、菜单、按钮及权限标识。
- 保存时提交选中的 `menuIds`。
- 支持展开全部、全选和清空普通角色权限。
- `admin` 角色显示系统保护状态，禁止编辑、删除和配置权限。

`system.js` 增加用户详情、角色权限查询和保存 API。

## 8. 错误处理

统一抛出 `BizException` 并由全局异常处理返回 `Result`：

- 用户名已存在。
- 角色编码已存在。
- 角色不存在或已停用。
- 菜单权限不存在或已停用。
- 非超级管理员试图授予或撤销 `admin`。
- 试图破坏最后一个有效超级管理员。
- 试图修改受保护的 `admin` 角色。

任何事务步骤失败时，用户、角色和关联表操作整体回滚。
