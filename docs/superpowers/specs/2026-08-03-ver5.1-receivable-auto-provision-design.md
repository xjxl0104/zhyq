# ver5.1 应收导入·预览确认式自动建档 — 设计文档

- 日期:2026-08-03
- 分支基线:ver5.0(= ver4.3 + 项目切换)
- 目标版本:ver5.1

## 1. 背景与目标

ver4.3 的应收导入解析成功,但真实工作簿的租户/空间在系统主数据里不存在,导致 9 行全部 `NEEDS_BINDING` 无法入库。核心原则(用户明确):**系统为表格服务、表格是权威数据来源**;将来新增租户也走同一套。

**目标**:在导入预览阶段,识别"表格里有、系统里没有"的租户与空间,列成"待创建清单"给用户确认;确认后系统批量建档(租户去重 + 合成空间/房源),自动绑定,并允许**合同留空**(先登记、不生成账单,待日后关联合同再补)。

## 2. 关键决策(已确认)

| # | 决策点 | 选定 |
|---|--------|------|
| 1 | 建档方式 | **预览确认式**(非静默自动):列待创建清单 → 用户确认 → 批量建 |
| 2 | 建档层级 | 建**租户(按 name 去重)** + **空间/房源** |
| 3 | 租户名清洗 | 只剥**半角括号**状态后缀(如 `(新)还未签合同`);**保留全角括号**法定名(如 `（广州）`) |
| 4 | 合同 | **留空可后补**:放宽两处校验,允许 contract=null 入库;空合同则登记但**不生成账单** |
| 5 | 空间建法 | **A 合成空间**:统一"DIPARK"项目下建楼栋+楼层+以整串命名的房间,保证可绑定入库 |

## 3. 真实数据事实(设计依据)

- 9 数据行,**6 个去重后租户**:李万能、广州昌泰供应链科技有限公司、广州鑫晨供应链有限公司、广州微新供应链管理有限公司、中印国际供应链（广州）有限公司、广东云山供应链科技有限公司(占 row9-12 共 4 行)。
- 楼层列样例:`DIPARK第六层的储存区一`、`DI PARK数智云仓产业园第二层`——无楼栋、无房号;"DIPARK" 与 "DI PARK数智云仓产业园" 为同一项目两种写法 → 归一到一个项目。
- `fin_receivable_register.contract_id` DB 层可空(V32 第39行),确认入库路径已容忍 null;仅两处 Java 规则拦截。

## 4. 需要改动的代码(基于探查)

**放宽合同校验(2 处):**
- `ReceivableBindingValidator.validate()` 第32-34行:去掉 `contractId == null` 的拦截;当 contractId 非空时才做"合同-租户一致""合同-项目定位空间"校验。
- `ReceivableImportService.bindRow()` 第144-146行:`bindingComplete = tenantRefId != null && (spaceId != null || roomId != null)`(移除 `&& contractId != null`)。

**建档服务(新增):** `ReceivableProvisionService`
- `previewMissing(batchId)`:扫描批次各行,产出"待建租户"(去重、清洗后名+原名)与"待建空间"(去重整串)清单。
- `provision(batchId, confirmations)`:按用户确认批量建租户/空间/房源 → 调 `spaceSync.sync(...)` → 回填各行 tenantRefId/roomId/spaceId。

**账单生成:** 合同为空的登记,`confirm` 入库但**跳过账单生成**;登记状态标"待关联合同"。

## 5. 建档规则细节

**租户去重与清洗:**
- 清洗:去掉**半角**括号及其中状态词的后缀,正则仅匹配行尾 `\([^)]*\)` 且不动全角 `（）`。示例:`广州昌泰供应链科技有限公司(新)还未签合同` → `广州昌泰供应链科技有限公司`;`中印国际供应链（广州）有限公司` **不变**。
- 去重键:清洗后的 name。同名只建 1 个租户(云山 4 行 → 1 租户)。
- 建档字段:`name`=清洗后名;`tenant_type`:名称含"公司/有限/企业/厂/中心/店/合作社"等企业关键字 → 1(企业),否则 → 2(个人)(如"李万能"→个人);默认可在预览清单里由用户改;`status`=1;`code`=生成唯一值(`AUTO-` + 时间戳/序号);先查 `biz_tenant` 是否已存在同名(未删除),存在则复用不新建。

**空间(合成)建法:**
- 项目:归一到一个"DIPARK"项目(名称含 "DIPARK"/"DI PARK" 视为同一);系统已有则复用,否则新建 `biz_project`。
- 楼栋:该项目下建/复用一个合成楼栋(如 `DIPARK主楼`)。
- 楼层 + 房间:每个不同的楼层整串建/复用一个 `biz_floor`(name=整串)+ 一个 `biz_room`(`room_no`=整串,`code`=生成唯一),四级 id 齐全。
- 建完对新建的 building/floor/room 依序调 `spaceSync.sync("building"/"floor"/"room", id)`,确保进入 `sys_space`,否则绑定校验报"房间尚未同步"。

## 6. 数据流 / 交互(前端)

沿用 ver4.3 三段式,前面加"补建"环节:

```
上传 → 解析预览(9行,NEEDS_BINDING)
     → [新] 系统列出「待创建租户 6 / 待创建空间 9」清单
          · 每项显示 原值 → 建档值,用户可改名、可勾"复用已有"
     → 用户确认建档 → 系统批量建租户/空间/房源 + 同步空间树 + 回填绑定
     → 行变为 VALID(合同空的标「待关联合同」)
     → 确认入库(有合同的生成账单;无合同的仅登记)
```

前端在 `ReceivableRegister.vue` 的导入向导里新增一步"补建主数据",调用两个新接口:
`GET /finance/receivable/import/{batchId}/provision/preview`、`POST /finance/receivable/import/{batchId}/provision`。

## 7. 非目标(YAGNI)

- 不做空间树的精细化(楼栋/分区拆解);合成空间够跑通,精细化另立需求。
- 不做租户名模糊匹配自动合并(只精确同名去重),避免"昌泰/昌记"错并。
- 不自动建正式合同(风险最高);合同留空、后补关联。
- 不改 ver4.3 的解析器(HEADERS 已匹配真实表)。
