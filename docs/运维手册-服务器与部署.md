## 一、怎么连上服务器

已经配好了，直接用：

```bash
ssh aole
```

就这一条，不需要密码，不需要验证码。

### 背后做了什么（重装系统或换电脑时需要重做）

私钥放在 `C:\Users\xjxl\.ssh\aole-prod.pem`（原件在微信文件目录里，见文末安全提醒）。
Windows OpenSSH 强制要求私钥 ACL 收紧，否则报 `UNPROTECTED PRIVATE KEY`：

```powershell
icacls "$env:USERPROFILE\.ssh\aole-prod.pem" /inheritance:r /grant:r "$($env:USERNAME):(R)"
```

`C:\Users\xjxl\.ssh\config` 里配了别名，所以能简写成 `ssh aole`：

```
Host aole
    HostName 121.40.120.226
    User root
    IdentityFile ~/.ssh/aole-prod.pem
    IdentitiesOnly yes
    ServerAliveInterval 30
    ServerAliveCountMax 6
    TCPKeepAlive yes
```

### 几个容易踩的坑

**阿里云控制台进不去，也不需要进。** 控制台的 Workbench 要账号绑定手机/邮箱的动态验证码，服务器上没有任何东西能生成它。三条控制台路径 2026-08-15 实测全不通：Workbench 要验证码；RAM 子账号 `wmz0423@31547917.onaliyun.com` 登不进控制台（很可能创建时只开了 OpenAPI、没勾控制台密码登录）；手上那把 AccessKey 属于 RAM 用户 `certbot`（证书机器人），没有 ECS 运维权限。

**SSH 是完全独立的通道**，走 SSH 协议层认证，跟控制台那套验证码无关。SSH 能做的事 Workbench 一件都不多——Workbench 只是浏览器里的终端。

**`dogs.pem` 是别的机器的**，对这台会报 `Permission denied (publickey)`，别浪费时间。

**Windows 上给服务器传多行脚本要用 base64**，直接传单引号/括号会被 PowerShell 吞掉导致语法错误：

```powershell
$s = @'
你的多行 bash 脚本
'@
$b = [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes($s))
ssh -o BatchMode=yes aole "echo $b | base64 -d | bash"
```

## 四、代码怎么上线

### 全自动：推 GitHub 就行

`/opt/zhyq/deploy.sh` 由 cron 每 5 分钟跑一次，自动找**版本号最大的 `ver*` 分支**，发现远端有新 commit 就拉下来重建容器。

### ⚠️ 开新版本分支：必须从最新的已发布分支切

因为部署只认**版本号最大**的 `ver*` 分支，一旦新分支从旧基线切出去，它一上线就会把之间所有已发布的功能顶掉——线上表现为功能凭空消失，且不会有任何报错。

**规则：开 `verX.Y` 之前，先确认它的起点是当前版本号最大的那个 `ver*` 分支。**

```bash
# 正确：从当前最高版本切
git fetch origin
git ls-remote --heads origin 'refs/heads/ver*'   # 先看清最高的是哪个
git checkout -b ver6.9 origin/ver6.8             # 从它切,不要从 ver6.4 之类的旧分支切
git push -u origin ver6.9
```

如果新分支已经从旧基线切出去了，别删旧分支去"让位"——**把旧分支合并进新分支**，两边工作都保住：

```bash
git checkout ver6.9
git merge origin/ver6.8      # 把落在旧分支上的功能带过来
# 解冲突 → 跑测试 → push
```

**同样别随意删除 `ver*` 分支。** 删掉当前最高版本分支，等于让部署回退到次高版本，效果和上面一样：线上功能静默消失。分支即使不再开发也应保留，它是那个版本的发布锚点。

> 2026-08-29 当天线上功能被顶掉两次，根因都是这一条：`ver6.7`/`ver6.8` 从 `ver6.6` 合入新功能**之前**的提交分叉，随后 `ver6.6`、`ver6.8` 又被删除，部署落回不含新功能的分支。代码一行没错，全是分支拓扑导致的。

所以正常流程只有一步：

```bash
cd F:/智慧园区代码
git add -A backend/src frontend/src
git commit -m "fix(xxx): 说明"
git push origin ver6.4
```

推完 5 分钟内自动上线。想立刻上线：

```bash
ssh aole "cd /opt/zhyq && setsid nohup ./deploy.sh >> /opt/zhyq/deploy.log 2>&1 < /dev/null &"
```

代码没变但要重建镜像（比如改了 Dockerfile、或上次构建失败）：

```bash
ssh aole "cd /opt/zhyq && setsid nohup ./deploy.sh --force >> /opt/zhyq/deploy.log 2>&1 < /dev/null &"
```

### 看部署结果

```bash
ssh aole "grep -E '部署完成|!! |回滚|后端就绪' /opt/zhyq/deploy.log | tail -5"
```

成功长这样：`=== 部署完成: ver6.4@083ea4e ===`，前面一行是 `后端就绪 (36s, HTTP 200)`。
构建约 4 分钟（Maven 打包 + pnpm build，`--no-cache`）。

### 脚本的保护机制（都实测过）

- **构建失败不换容器**，旧版本继续服务，日志出现 `!! 构建失败, 保持旧容器运行`
- **后端 90 秒起不来自动回滚**到上一个镜像
- **flock 单实例锁**，上一轮还在构建时这一轮直接跳过，不会并发
- **保护服务器本地配置**：`backend/Dockerfile`、`frontend/Dockerfile`、`docker-compose.full.yml`、`backend/settings.xml` 这四个文件在服务器上有本地改动（阿里云 Maven 镜像、npmmirror、`zhyq-edge` 外部网络），checkout 会覆盖它们，脚本每轮先备份再还原，日志里会打 `已还原本地构建配置: ...`。**不要试图把这些本地改动提交到仓库**，它们是环境相关的。
- **GitHub 不可达时静默重试**，只在状态变化时记一条日志，不刷屏

## 五、本地怎么构建验证

**JDK 必须用 17。** 本机 `JAVA_HOME` 指向 JDK 24，跟 Lombok 不兼容会编译失败。用 `.tools` 下自装的：

```bash
cd F:/智慧园区代码/backend
export JAVA_HOME="C:/Users/xjxl/.tools/jdk-17.0.19+10"
"C:/Users/xjxl/.tools/apache-maven-3.9.16/bin/mvn.cmd" -B -s "C:/Users/xjxl/.tools/settings.xml" test
```

`settings.xml` 里配了阿里云镜像，不加 `-s` 会很慢或超时。全量测试当前 185 项通过、1 项跳过（那项依赖本地 xlsx 文件，正常）。

前端：

```bash
cd F:/智慧园区代码/frontend
pnpm install --registry=https://registry.npmmirror.com
pnpm build          # 验证构建
pnpm dev            # 本地预览，端口 5273
```

注意 `pnpm dev` 的接口代理指向 `localhost:8090`，**本机没有 MySQL，后端跑不起来**，所以只能看页面结构，取数会失败、登录也过不去。要看真实效果就部署到线上看。

## 六、数据安全边界

**代码升级不影响数据。** 数据库在 Docker 命名卷 `zhyq_zhyq_mysql_data` 里，附件在宿主机 `/opt/zhyq/uploads`，两者都跟容器生命周期解绑。部署脚本只重建 `zhyq-backend` 和 `zhyq-frontend`，**不碰 `zhyq-mysql`**——所以部署好几轮之后 `zhyq-mysql` 仍然显示 `Up 5 days`。

**数据库结构变更是例外，会真的改库。** `backend/src/main/resources/db/migration/` 下的 Flyway 脚本在后端启动时执行，只往前不回滚。当前版本 **V39**，下一个可用版本号是 **V40**。加列建表安全，`DROP`/`UPDATE` 要格外小心。要动结构我会先说明改什么、可不可逆。

**项目之间是隔离的**：每个项目有独立的数据库容器和独立的 Docker 网络。zhyq 在 `zhyq-edge` 网络里，成员只有自己那三个容器加 `central-caddy`。别的项目连不到 zhyq 的库，反之也一样。

**唯一的公共入口是 `central-caddy`**（Caddy 2），对外只开 80/443，按域名分流。zhyq 的配置在 `/data/caddy/sites.d/zhyq.conf`，内容就是 `zhyq.aoleplat.com` 反代到 `zhyq-frontend:80`。各项目数据库端口一个都没暴露到公网。

## 七、已知问题与注意事项

**GitHub 连接不稳，这是这台机器的既有毛病。**

`git` 默认的 wire protocol v2 在这台机器上会挂死到超时，必须降级：

```bash
git -c protocol.version=0 -c http.version=HTTP/1.1 <子命令>
```

实测 v2 三次全部 40 秒超时、0 个 ref；加上 `protocol.version=0` 后 1 秒拿到 16 个 ref。日志里的 `HTTP2 framing layer`、`GnuTLS recv error`、`expected flush after ref listing` 都是这一个根因。`deploy.sh` 的 `git_net()` 里已经处理了。

另外该机到 `github.com:443` 的出网本身也间歇性不通（同一个 curl 有时 0.55 秒返回 200、有时 130 秒超时，实测 6 次里失败 2 次）。而 **SSH 到 github.com:22 实测 9 次全通、稳定 1.7 秒**——所以彻底解决办法是把 remote 换成 SSH 并配只读 deploy key，这件事还没做。内网 GitLab `124.71.29.81:8801` 从该机稳定可达，也可以做镜像仓库。

**没有备份，这是当前最大的风险。** 219MB 数据库 + 附件只存在这一块盘上，没有定期备份机制。`/root` 下有几个手工导出的 `.sql`/`.json`，不成体系。建议开阿里云快照，或加 cron 每天 `mysqldump` 到 OSS。

**明文凭据散落在微信文件目录。** `E:\APP2\微信记录\...\2026-07\` 下的 key 清单里，OpenAI、阿里云 AccessKey、GitHub token、RDS 密码全是明文。微信目录会被同步和备份，也可能被其他软件扫到。建议轮换一遍再挪到密码管理器。

## 八、常用排查命令

```bash
# 容器状态
ssh aole "docker ps --filter name=zhyq --format '{{.Names}} | {{.Status}}'"

# 后端日志（去掉栈帧噪音）
ssh aole "docker logs --tail 100 zhyq-backend 2>&1 | grep -vE '^\s+at '"

# 确认 Spring 起来了
ssh aole "docker logs zhyq-backend 2>&1 | grep -E 'Started ZhyqParkApplication|APPLICATION FAILED'"

# Flyway 当前版本
ssh aole "docker logs zhyq-backend 2>&1 | grep -iE 'Successfully applied|Current version of schema'"

# 磁盘
ssh aole "df -h / && du -sh /opt/zhyq/uploads"

# 线上实际在跑哪个 commit
ssh aole "git -C /opt/zhyq log --oneline -1"

# 线上前端产物是否最新（对比公网引用的文件名）
curl -s https://zhyq.aoleplat.com/ | grep -oE 'index-[A-Za-z0-9_-]+\.(js|css)'
```

## 九、当前进度（2026-08-16）

已上线（commit `083ea4e`）：

- 反馈页附件上传修复。根因是上传组件读 `localStorage` 的 `'token'`，而全站写入的 key 是 `'zhyq_token'`，请求带空 `Bearer` 被 Security 401 挡在 controller 外，文件从未落盘。改为用 `:http-request` 走 axios 复用拦截器。连带修了 `res.code === 200` 判断永远为假（成功码是 `0`、且拦截器已拆包）、nginx 缺 `client_max_body_size`（默认 1MB 会先于后端 413）、截图与附件共用 5 个上限但 UI 各写 `limit=5`。
- Element Plus 中文语言包。`main.js` 原先只传 `{ name: 'zh-cn' }` 没有词典，界面显示 `el.pagination.total` 这类裸 key，影响 15+ 个页面。
- 工单来源联动。`pm_work_order` 加 `source_type` + `source_id`，巡检/巡更/告警三条转单路径都写来源主键，工单详情可跳回源记录。**只对新工单有效**，存量工单迁移里只能回填来源类型，源记录 id 无从恢复。
- 工单汇总页 `/property/workorder-summary`。顺带修掉 `/stats` 只统计状态 1/3/5、漏 2/4/6/7 导致各项之和不等于 total 的 bug。注意 `stats.pending` 的口径已从"待派单"改为"在办合计"，取待派单要用 `pendingDispatch`。
- 责任单位主数据 `/property/responsible-unit`。新表 `pm_responsible_unit` + 工单外键，含 CRUD、Excel 导入（模板下载、表头强校验、预览、按名称 upsert）、报修表单下拉。**表目前是空的**，要先导入或手工建几条下拉才有内容。
