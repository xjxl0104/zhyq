# 2026-09-16 可交互动漫风首页实验

本次目标是实现一个可自由旋转、可动画、保留现有首页功能的动漫风版本。先前的图片演示只能平移、缩放和点击固定位置，不能满足这一要求。实验入口为本地开发页 `/dev/twin-anime.html`，复用真实首页组件和当前七层建筑模型。用户体验后已明确选择此版本替换正式首页，默认渲染现已改为动漫风；本地对照页仍可显式选择原版。

## 路线比较与选择

| 路线 | 画面与交互能力 | 当前适配成本 | 本次结论 |
| --- | --- | --- | --- |
| 分层图片、固定角度预渲染 | 可制作插画、热点、平移缩放、有限视差和角度切换；有限预制图片不能任意环绕，也不能直接复用当前楼层拆解和室内空间 | 需重新制作各角度、楼层和室内图片，并重建点击、遮挡和点位坐标 | 不作为满足完整交互要求的方案 |
| 当前三维模型 + Toon 光照 | 保留真实三维空间、任意环绕、楼层动画和点位投影，以色块明暗表现动漫风 | 可复用模型、控制器、页面与业务入口，主要修改材质和渲染流程 | 本次实验采用 |
| 低面数模型 + 手绘贴图，远景使用替身平面（impostor） | 可以保留三维交互，并进一步控制插画风格；替身平面需要处理方向、近景及遮挡 | 属于独立资产制作任务，需要重做拓扑、UV、贴图、距离细节和拾取代理 | 后续候选；质量和性能均需实测 |

“动漫风”是画面表达，“伪 3D”是空间实现方式，两者不能直接等同。在必须保留自由旋转、拆层、室内查看的前提下，本次选择保留三维功能结构，改变画面着色方式。这是基于当前项目代码和用户交互约束作出的工程选择，不是所有场景的通用结论。

## 依据与实验设计

- 使用 Three.js 原生 `MeshToonMaterial` 实现分段光照，材质继续共享，不为每个对象重复创建材质。官方接口提供 `gradientMap`，使用时要求最近邻过滤；具体配色和梯度属于本项目视觉实验。[MeshToonMaterial 官方文档](https://threejs.org/docs/pages/MeshToonMaterial.html)
- 保留现有 `facadeDetails.js` 的窗格、竖纹和抗摩尔纹处理，保留车辆顶点色、建筑和入口的照片字标。玻璃保持浅色透明，不因卡通化变成黑色实体板；继续尊重 `architectural-glass` 的透明度、关闭深度写入和不透明阴影约定。
- 本轮不叠加全场景轮廓线通道。仅在建筑外壳上添加 15 个随原楼层移动的线稿对象，共 1,792 条主要长边，过滤小于 1.5 米的细节，不描绘玻璃、文字或树叶。官方 `OutlineEffect` 是独立的卡通描边渲染效果，本轮采用有限建筑边线控制新增开销。[OutlineEffect 官方文档](https://threejs.org/docs/pages/OutlineEffect.html)
- 动漫实验直接调用 renderer 绘制，不走现有 GTAO / EffectComposer 流程；比较时使用相近且有上限的实际像素分辨率，记录画布尺寸和像素比，避免将单纯降低分辨率当成着色优化收益。动漫路径不需要生成 PMREM 环境贴图。
- 保留现有按需绘制：旋转、阻尼、楼层动画、相机过渡和界面状态发生变化时继续绘制；停止自动环绕且画面稳定后不重复绘制。按需渲染是官方针对静态查看类应用建议的节电方式；阻尼仍需持续更新到稳定。[Rendering on Demand 官方手册](https://threejs.org/manual/en/rendering-on-demand.html)
- 保留树木分区、三档距离细节和缓存阴影。树木切档、模型几何变化或天气变化时才按既有规则更新阴影，单纯环绕复用阴影缓存。共享材质、实例化、分区和已有合批边界保持不变。
- 不将七层楼和全部系统合成一个不可拆的对象。官方优化手册说明减少对象/绘制提交可以降低开销，同时指出合并后的局部对象不再容易独立移动；这里必须保留楼层拆解边界。[Optimize Lots of Objects 官方手册](https://threejs.org/manual/en/optimize-lots-of-objects.html)

调整材质和减少通道的实际收益取决于瓶颈。当前仍需下载、解析和绘制同一份 GLB，透明树叶覆盖、阴影、几何和业务界面仍然有开销；没有测量之前不宣称帧率或加载时间提升。

## 复用边界

页面沿用 `TwinDashboard.vue` → `TwinHome.vue` → `WarehouseScene.vue`，模型状态沿用 `warehouseController.js`。保留同一个模型资源、相机控制、七层结构、点位、页面面板和路由。

`WarehouseScene` 的现有契约不因画风变化而改变：

- 输入：`mode`、`floor`、`layer`、`weather`、`viewpoint`、`focused`、`rotating`、`markers`。
- 事件：`select-floor`、`select-point`、`open-module`、`ready`、`error`。
- 暴露方法：`reset()`、`zoom(amount)`、`exportModel()`。
- 模型保留 `twinRole` 的 `building`、`site`、`roof` 和七个 `floor`；每层仍有 `shell`、`structure`、`interior`、`fire`，网格继续携带 `userData.floor`。
- 点位使用世界坐标经相机投影定位，并随拆层高度变化。不得改成只适合某一张插画的固定屏幕百分比。

若替换材质，需在天气模块收集材质引用前完成，或同步更新其引用；否则夜景可能仍修改旧玻璃、旧灯具材质。共享资源应由明确的所有者释放，不重复释放原模型材质。

## 本地演示与数据边界

新入口复用 `frontend/dev/twin-layout.js` 的隔离验证方式：真实 Layout、Pinia、Element Plus 和首页组件，使用内存路由与请求适配器。`/building/project/list` 返回两个示例项目，其他请求返回示例空响应，业务链接进入显示路径的本地模块占位页；该页面不连接真实后端、不创建登录凭据。

运营数字、出租率、事项、合同和设备状态仍是示例；夜景/晴天是视觉模拟，视频及实时设备接入仍待真实平台连接。功能入口保留不代表已接通真实业务数据。正式应用继续使用原有鉴权及业务路由。

GLB 不保存任意运行时 shader，也不保证还原 Toon 分段光照。导出时在模型快照上回退到原始可导出材质，保留当前几何、楼层和可见状态；这是可编辑模型导出，不是将浏览器动漫画面原样打包。原有解析立面细节仍通过 extras 在本项目加载时恢复。

## 验证与测量记录

既有交互测试位于 `TwinHome.spec.js`、`WarehouseScene.spec.js`、`warehouseModel.spec.js`、`TwinDashboard.integration.spec.js`、`sceneWeather.spec.js`、`warehouseAsset.spec.js`、`parkTreeLod.spec.js` 等文件。实验还需检查原始材质回退、玻璃与立面细节保持、天气切换及新增资源释放。

- 本地测量在切换标签、离开场景或切换项目时取消并清空旧值；GPU disjoint 会丢弃整批未完成查询。没有将后台暂停时间计算成卡顿。

### 本机连续环绕采样（2026-09-16）

同一 Codex 内置浏览器，视口 1440×1000，实际场景像素均为 1151×772；外观、全部楼层、晴天、专注模型、关闭点位、开启自动环绕。构建与测试结束后分别复位镜头、采样约 10 秒，页面保持前台。两次起点相近，未实现严格同步相机轨迹。GPU 值为每秒最近 90 次有效绘制的中位数，再对 10 个样本取平均；CPU 值为渲染调用的平均提交时间，不含所有业务 UI 工作。

| 指标 | 原版对照 | 动漫三维 |
| --- | ---: | ---: |
| 实际绘制帧/秒 | 50.0 | 50.0 |
| CPU 渲染提交时间 | 1.19 ms | 1.37 ms |
| GPU 绘制时间 | 3.65 ms | 1.68 ms |
| 每帧绘制调用（平均） | 161 | 175 |
| 每帧绘制三角形（平均） | 166,009 | 171,585 |

本机两种方案都达到当时约 50 帧/秒，不能宣称帧率翻倍。动漫模式的 GPU 时间较低，CPU 提交和绘制次数略高（新增建筑边线），三角面数因取景、剔除和树木 LOD 也有差异。这轮仅说明该方案在本机的持续环绕具有降低 GPU 开销的潜力；不是同事低配电脑的验收结果，也没有验证冷启动提速。原版运动时已跳过 GTAO，差异不能全部归因于移除 GTAO。仍需在目标设备测试拖动、拆层、首次加载与高分屏。

## 用户确认后的正式首页切换

用户已明确要求用动漫版替换写实首页并推送。`WarehouseScene.vue` 默认选择动漫材质、直出渲染、2048 阴影贴图和动漫天气；原来的控制器、楼层、点位、业务路由及导出入口保持原契约。本地对照页可切回写实模式；该开关、测速模块和演示请求适配器不进入正式页面。品牌修正为 DIPARK 六个字形，模型文件已重新生成。

发布前在最新 `origin/test`（43549cd，已进入 main）的基线上完成：

- 全量前端 Vitest：39 个文件、152 项测试通过；包括默认动漫路径、DEV 原版对照、导出克隆与资源释放回归。全量检查发现既有上传组件测试缺少 Pinia，已仅修正测试挂载配置，未改业务实现。
