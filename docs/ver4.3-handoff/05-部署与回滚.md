# 部署与回滚

## 一、升级前

1. 备份生产数据库和宿主机 `uploads`。
2. 确认当前运行版本为 ver4.2，记录现有用户、超级管理员、角色和用户角色关联数量。
3. 在 `.env` 中配置长期固定的 `ZHYQ_FIELD_ENCRYPTION_KEY`，值必须为 Base64 编码的 32 字节密钥。
4. 设置强随机 `JWT_SECRET`、数据库密码、正式 CORS 域名和售货机 HTTPS 地址。
5. 不把 `.env`、数据库备份或用户工作簿提交到 Git。

## 二、升级

```bash
git fetch origin
git checkout ver4.3
git pull --ff-only origin ver4.3
docker compose -f docker-compose.full.yml config
docker compose -f docker-compose.full.yml up -d --build
docker compose -f docker-compose.full.yml logs --tail=200 backend
```

后端启动时 Flyway 会从 v31 继续执行 V32、V33。成功日志应显示数据库版本为 v33。升级后让管理员退出并重新登录，使 JWT 重新载入新增权限。

## 三、业务启用顺序

1. 按现有部署文档先完成统一空间树 reconcile 和历史空间回填。
2. 在“财务 → 应收明细登记表”上传工作簿，仅做预览。
3. 为每行选择并确认租户、合同和空间/房间；服务端会再次验证对应关系。
4. 全部行校验通过后，由有确认权限的管理员确认入库。
5. 先抽查免租、折扣、抵扣、物业费和保证金，再生成账单。
6. 在“应用中心 → 自动售货机”下载系统标准模板，按机器、销售、补货、故障、对账分别小批量试导入。

## 四、业务批次回滚

- 应收批次只有在未生成下游账单、没有后续财务数据且仍是最后写入批次时才能撤销。
- 修订应收撤销后恢复导入前登记、规则和保证金快照；首次新增的登记则删除。
- 售货机批次只有在记录仍由该批次最后写入时才能撤销；更新记录恢复旧值，新增记录逻辑删除。
- 已被后续批次覆盖的旧批次，无论从页面还是直接调用 API 都会被拒绝。
- 不直接改业务表，不删除 Flyway 历史，不手工伪造批次状态。

## 五、应用回退

应用镜像可临时回到 ver4.2，但 V32/V33 数据表和 Flyway 记录应保留。回退期间不要使用 ver4.2 代码修改 ver4.3 新表。重新恢复 ver4.3 时必须继续使用同一字段加密密钥，否则历史收款账户无法解密。

更完整的环境变量和容器说明见 [`../DEPLOY.md`](../DEPLOY.md)。
