# #3 统一空间树主数据设计（叠加层 sys_space）· 待审阅

> 版本 v0.1（2026-07-15）· 状态：**待用户审阅**，通过后再派 Opus 编码 + Fable 审查
> 落地方式已定（用户拍板）：**叠加层 sys_space**（新建统一空间表，映射现有四层 + 预留扩展节点类型）；业务表加可空 `space_id` 逐步回填，**旧 roomId 外键原地不动、双写过渡**
> 约束：本文只做设计，不含代码；编码前此文档需你确认。项目**无测试**，改动遵循"零触碰既有 building/contract/finance 逻辑"原则。

---

## 1. 目标与非目标

**目标**：给现在"project→building→floor→room 四张独立表、各业务模块各自用 roomId 外键引用"的空间数据，叠加一棵**统一空间树主数据 `sys_space`**：统一编码、统一父子关系、支持子树聚合查询（能耗/告警按任意空间层级汇总），并为后续「资产管理#20 / 便捷通行#21」等新模块预留挂树位。

**非目标（本期不做）**：
- 不实做 园区/区域/楼群/公共区域/资产位 等**新节点类型的录入界面与业务**（type 只留枚举位，本轮只映射现有四类）。
- 不重写既有 contract/workorder/energy/iot 的 roomId 外键（那是"彻底改造"方案，已否决）。
- 不改 building 四表结构，不改房态/租控/合同锁房源等既有逻辑。

---

## 2. 现状锚点（来自探查，编码时对齐）

- 空间四表：`biz_project` / `biz_building` / `biz_floor` / `biz_room`（`@TableName` 实测）。`Room` 实体已冗余父链 `projectId/buildingId/floorId` + `code` + `roomNo` + `status`（0未配置1可租2锁定3意向4签约中5在租6退租处理中7维修8停用）。
- building 模块**无 service 层**，四个 controller（Project/Building/Floor/Room）直接注入 mapper 做 CRUD。
- 引用 room 的业务表（真实表名）：`biz_contract`（+ 关联表 `biz_contract_room` 多房源）、`pm_work_order`、`eng_reading`（+ `eng_meter`）、`iot_device`（+ `iot_alarm`）。
- 已有基础设施可复用：`common/event/` 领域事件（批次①）、`BaseEntity`（tenant_id/审计/version/deleted 自动填充）、`@Scheduled` 可用（Spring Boot 3.2）。
- **新 mapper 必须放 `*.mapper` 包**（主类 `@MapperScan("com.zhyq.park.**.mapper")`，运行期扫描，放错编译过但启动崩——这是批次② 502 的教训）。

## 3. 表结构设计（新表 + 业务表加列，走 Flyway V19）

### 3.1 sys_space（统一空间树主数据，新表）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | 空间节点主键（**与旧表主键不同一命名空间**，靠 ref 关联） |
| parent_id | bigint | 父节点 id，根节点为 0 或 null（邻接表：建树/拖拽/直接父子） |
| path | varchar(255) | 物化路径，形如 `/1/5/23/`（**子树聚合查询靠它**：`WHERE path LIKE '/1/5/%'` 一次取全部后代） |
| level | tinyint | 层级深度（1=根），冗余便于按层查询/校验 |
| type | varchar(16) | 节点类型枚举：**本期 PROJECT / BUILDING / FLOOR / ROOM**；预留 PARK / ZONE / AREA / PUBLIC / ASSET_LOC（枚举位，本轮不实做录入） |
| code | varchar(64) | **统一空间编码**，全表唯一（见 §3.3 编码规则），供跨模块引用与人读 |
| name | varchar(128) | 显示名（取自旧表 name/roomNo） |
| ref_type | varchar(16) | 指回旧表：project / building / floor / room |
| ref_id | bigint | 旧表主键（`ref_type + ref_id` 唯一，保证一个旧对象只映射一个空间节点） |
| sort | int | 同级排序 |
| status | tinyint | 1正常 0停用（与旧表状态解耦，仅控制树展示） |
| （BaseEntity 公共字段） | | tenant_id / create_by / create_time / update_* / version / deleted，MyMetaObjectHandler 自动填充 |

**索引/约束**：
- 唯一键 `uk_ref (ref_type, ref_id, deleted)`（防重复映射，deleted 参与见项目 V9 惯例）。
- 唯一键 `uk_code (code, deleted)`。
- 普通索引 `idx_parent (parent_id)`、`idx_path (path)`、`idx_type (type)`。

### 3.2 业务表加可空 space_id（本期最小集，5 张表）

> 只**加列 + 建索引 + 回填**，不加数据库外键约束（项目现有风格即无 FK 约束，靠应用层），不动 roomId 列。

| 表 | 新增列 | 回填来源 |
|---|---|---|
| `biz_contract` | `space_id bigint NULL` | 该合同主房源 roomId → sys_space(ref_type=room).id |
| `biz_contract_room` | `space_id bigint NULL` | 每条 roomId → 对应 room 空间节点（多房源逐条） |
| `pm_work_order` | `space_id bigint NULL` | roomId → room 空间节点（roomId 可空的工单则留空） |
| `eng_reading` | `space_id bigint NULL` | 经 `eng_meter` 关联的 roomId → room 空间节点 |
| `iot_device` | `space_id bigint NULL` | roomId → room 空间节点 |

`iot_alarm` 本期不加列——告警按空间聚合时经 `iot_device.space_id` 关联即可（避免冗余双份，减小回填面）。

各表加 `idx_space_id`。**旧 roomId 列与其所有既有查询原地不动**：space_id 是"新增的可选维度"，任何未迁移的老代码路径完全无感。

### 3.3 统一空间编码规则（code 生成）

编码由父链拼接派生，稳定可读、全局唯一：

```
PROJECT   P{projectCode}
BUILDING  P{projectCode}-B{buildingCode}
FLOOR     P{projectCode}-B{buildingCode}-F{floorCode}
ROOM      P{projectCode}-B{buildingCode}-F{floorCode}-R{roomCode}
```

- `{xxxCode}` 优先取旧表已有 `code` 字段；旧表该行无 code 时回退用其 id（形如 `P#12`），保证不冲突。
- 编码在 `SpaceSyncService` 里生成，回填与增量同步共用同一套 derive 逻辑（单一函数，避免两处漂移）。

## 4. 同步机制（叠加层核心：SpaceSyncService）

`space/service/SpaceSyncService`（单 @Service），三种触发，共用一套 upsert：

1. **一次性回填 `reconcile()`**：按 project→building→floor→room 顺序全量扫旧表 → 逐层 upsert sys_space 行（先建父后建子，保证 parent_id/path 正确）→ 幂等（按 `uk_ref` upsert，重跑不产生重复）。首次通过 Flyway 之后的一个 `CommandLineRunner`（或手动调 `POST /space/reconcile`）执行一次。
2. **增量同步 `sync(refType, refId)` / `remove(refType, refId)`**：在 building 四个 controller 的 add / update / delete 成功后就地加一行调用。
   - building 无 service 层，此处是**唯一对既有 building 代码的改动**——仅在 CRUD 末尾追加同步调用，不改其原有增删改逻辑本体。
   - 删除采用逻辑删除（sys_space.deleted=1），与旧表逻辑删除对齐；有子节点时按旧表既有的删除校验行为为准（本层不额外拦截）。
3. **兜底对账 `@Scheduled` 夜间全量 `reconcile()`**：抓增量遗漏/手工改库导致的漂移，纯补偿，幂等安全。

> 双写含义澄清：sys_space 是旧四表的**投影 + 主数据层**，旧表仍是空间基础信息的写入入口（房态、面积等继续走 room 表）；sys_space 只维护"树结构 + 统一编码 + ref 映射"。业务表的 space_id 在新写入/迁移时与 roomId **同时写**（双写），读侧新功能用 space_id、老功能继续用 roomId。

## 5. 查询 API（SpaceController，全部只读，新增不改旧）

`space/controller/SpaceController`，前缀 `/space`：

| 接口 | 说明 |
|---|---|
| `GET /space/tree` | 返回完整空间树（parent_id 组装，或按 path 排序前端组树），供树控件 |
| `GET /space/children?parentId=` | 懒加载子节点 |
| `GET /space/{id}/subtree-ids` | 返回该节点及全部后代的 id 集合（`path LIKE`），**供能耗/告警/工单按空间聚合** |
| `GET /space/{id}/path` | 面包屑（根→该节点） |
| `GET /space/by-ref?refType=room&refId=` | 由旧对象反查空间节点（迁移期桥接用） |

聚合用法示例：能耗按"某楼栋"汇总 = `subtree-ids` 拿到该 building 下所有 room 空间节点 → 反查这些节点的 `eng_reading.space_id`。此前只能靠 room 表冗余父链手工 join，现在走统一子树查询。

## 6. 对既有逻辑的"零触碰"证明 & 回退方案（关键，无测试）

**零触碰证明**：
- sys_space 是**新表**，旧四表结构与数据一字不改。
- 业务表只**加可空列**，默认 NULL；所有既有 SQL（select 显式列 / MyBatis-Plus 按实体列）不受影响，房态、合同锁房源、账单、租控图等既有链路完全无感。
- 对 building 代码的唯一改动是 CRUD 末尾**追加**同步调用，包裹 try-catch 吞异常（同步失败不影响 building 主操作成功，靠夜间对账补偿）——即便 SpaceSyncService 抛错也不会让原有建楼/改房失败。

**回退方案（改崩怎么退）**：
1. 摘掉 building controller 里的同步调用 + 停用 `@Scheduled` → 系统立即回到"无空间树"的旧状态，业务零影响。
2. 业务表的 space_id 列留空不用即可（可选：`ALTER TABLE ... DROP COLUMN space_id`）。
3. `DROP TABLE sys_space` 不影响任何旧表与业务数据。
4. 因是纯叠加、旧 roomId 全程为准，**不存在"数据迁移不可逆"风险**（与 #7 的密码重置不同）。

## 7. 待你拍板的决策点

- **D1 回填触发方式**：`CommandLineRunner` 启动自动跑一次 reconcile（省事，但每次启动扫全表），还是只提供 `POST /space/reconcile` 手动触发（可控，推荐）？夜间 `@Scheduled` 兜底两者都建议保留。
- **D2 业务表迁移范围**：本期就加 contract / contract_room / work_order / eng_reading / iot_device 这 5 张（推荐，够 #8 规则派单/能耗告警聚合用），还是先只加 contract + work_order 两张最核心的、其余等 #8/#20/#21 用到再加？
- **D3 编码规则**：§3.3 的 `P..-B..-F..-R..` 拼接编码是否合口味？还是你有既定的园区空间编码标准（如国标/集团编码）要对齐？
- **D4 同步失败策略**：building CRUD 追加的同步调用失败时——吞异常靠夜间对账补（推荐，不阻断主业务），还是同事务内失败即回滚建楼操作（强一致但侵入 building 事务）？

## 8. 编码工作量预估（供排期）

sys_space 建表 + 5 业务表加列（Flyway V19）+ SpaceEntity/Mapper（放 `space/mapper`）+ SpaceSyncService（reconcile/sync/remove/编码 derive）+ SpaceController 5 只读接口 + building 四 controller 各加同步调用 + 一个 `@Scheduled` 兜底。约 Opus 半批工作量。Fable 重点审：①回填 SQL 的父子顺序与 path 正确性；②building CRUD 追加调用是否真的无副作用（事务边界、异常吞掉是否合适）；③业务表加列后既有查询无影响的抽样确认。前端"空间树选择器组件 + 树管理页"可作为后续增量（本设计只出后端主数据与只读接口）。
