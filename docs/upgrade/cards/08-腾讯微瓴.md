# 对标卡片：腾讯微瓴（智慧建筑/园区操作系统 + 微瓴同业开放平台 WeilingWith）

**资料充分度**：中高：D2编排与D4开放架构有腾讯云官方文档（产品1693系列+数字空间API文档）双重佐证，节点类型、指标发布流程、编码体系均来自官方一手文档；不足在于微瓴视图五大模块的完整清单、生态SaaS应用全目录无公开页面，底座无公开可注册demo，前端细节部分依赖官方描述与发布会报道，IOC模板数量存在9/11两种口径。

## 定位与目标用户
腾讯自2013年打造的"智慧建筑操作系统"（物联网类OS + 数字孪生底座），定位是建筑/园区的连接与开放PaaS：南向接入楼宇子系统与百万级设备（协议覆盖超90%），中间做空间建模与数据融合，北向以OpenAPI和零代码编排开放给生态。目标用户不是终端物业，而是行业生态伙伴——集成商、应用开发商、设备厂商、地产/园区业主IT团队；腾讯自己只做底座和少量标杆应用（微瓴视图/滨海大厦），场景应用交给合伙人生态（产品/行业/服务合伙人，LinkBase交付规范）。

    - 指标管理（原子指标 / 衍生指标）

  - 主数据管理（集成HR/企业微信/钉钉人员数据）
  - 零代码场景编排（IOC主题模板9~11个，二三维孪生场景一键生成）
  - 应用管理
  - 资源管理（资源服务目录、API集中授权给北向应用）

## 核心业务流程编排
微瓴的流程编排不走"审批流"路线，而是走"数据/设备联动编排"路线，核心是数据融合模块里的画布式零码编排（dtwin.tencent.com，数据融合>工作台>场景搭建）：
1) 联动流程编排：拖节点+连线，官方文档示例节点四类——查询设备影子（数据输入/触发，按设备类型+空间区域圈定）、逻辑判断（条件，如CO2/温度阈值）、查询附近设备（空间语义查询，找目标设备）、IOT服务-设备控制（动作，下发指令）。连线后"部署流程即生效"。典型场景：会议室CO2超标→自动开附近新风；消安联动；VIP访客到访跨系统联动。空间语义节点（查询附近设备）是特色——动作对象不是写死的设备ID，而是"该空间附近的某类设备"。
2) 指标编排发布API：设备原始数据→解析模型（结构化）→原子指标（分钟级聚合）→衍生指标（小时级统计），在画布上搭实时计算流程后"发布为API，注册到资源服务目录"，再由资源管理授权给北向应用消费（如IOC看板的24小时人流趋势）。预置能源/告警/门禁/安防/照明/停车等主题API指标模板和联动场景最佳实践模板，可直接部署即用。
3) 事件闭环：滨海大厦案例"事件触发的工作闭环"——设备告警→报警中心按message_type路由给相应应用→三维空间定位→处置（工单/联动），告警API含状态处理、处理记录、告警收敛。
4) 云边规则下发：云上完成编排配置后把规则打包成边缘节点下发，边缘本地跑规则、断网自治，交付后可远程改配置重新下发。
5) 连接器思路：设备侧靠"对象模型"（公共模型+项目自定义customModelId）做语义标准化，设备影子（desired/reported）做异步控制闭环；业务系统侧有专门的"业务系统数据接入"通道；应用间靠message_type消息类型做路由/广播/定向投递，实现应用解耦。

## 前端形态
微瓴自身是PaaS，前端形态分三层：1) 底座工作台（dtwin.tencent.com，需租户账号，无公开注册demo）：偏"工具型"而非表格后台——空间编辑器是浏览器内在线CAD导入+三维建模工具；场景搭建是节点连线画布；能碳管理支持"三维组件拖拉拽搭能源系统原理图"。2) IOC/大屏：零代码场景编排内置9~11个建筑园区IOC主题模板（不同期文档口径为9或11个），数据接入后"一键生成"二三维孪生大屏，支持继续拖拽改造；这是把大屏从定制开发变成模板+配置。3) 官方SaaS微瓴视图：基于BIM的三维数字孪生界面，"微瓴标准UI"，主系统同时兼容大屏与PC端，配套web与移动端（小程序做工单/告警移动处理、设备反向控制、掌上指标、消息触达）；所有异常事件以三维空间定位呈现（"以空间为索引完成业务闭环"），区别于传统IBMS的表格式管理。官网 weilingwith.tencent.com 有产品可视化演示入口（需申请）。整体设计体系强调"空间即界面"：设备、事件、工单都锚定在三维空间树上，而非纯列表。

## 架构与功能设计要点
闭源商业产品，无公开仓库。架构分层（官方文档/发布会一致口径）：连接层（物联感知：多协议适配、边缘接入工具、设备影子）→ 平台层（空间建模+数据融合+主数据，"人-设备-空间-业务"四要素全域数据模型，把空间数据/IoT数据/业务数据融成孪生体）→ 应用层（零代码/低代码"积木化应用组装"）。关键设计点：1) 统一编码体系是全平台骨架——wId全局唯一ID可指建筑/楼层/房间/设备/人/车，POIID用编号前缀表达空间父子层级，poiCode分类编码（m空间类/w设备类），level 6建筑/7楼层/8房间/9设备点；一切API围绕空间层级查询。2) 微服务边界原则明确：每服务独占一个端到端业务场景与自己的数据库，服务间不共享数据，靠API/消息互通。3) 开放接口四个方向：南向设备/子系统接入、北向资源服务授权（OpenAPI按需授权数据范围给EOA/IOC/ESG应用）、横向集成企业存量系统（HR/企微/钉钉）、云边（云上API支撑SaaS、边缘API支撑本地应用）。4) 多租户：公有云按"租户→项目→功能模块"组织，项目空间内分角色授权成员；另支持私有化和云边协同混合部署。5) 扩展点：项目自定义对象模型（customModelId覆盖公共模型）、自定义空间边界、自定义聚合指标（aggCustomId）、编排发布自定义API进资源目录。6) 生态架构：LinkBase=架构+敏捷交付规范+商业模式，场景栈八大场景（综合态势/智慧安防/边界通行/资产管理/能效管理/设施管理/环境感知/智能预警）交由合伙人实现。

## 可借鉴点 TOP5
- **[D2流程编排]** 照抄微瓴四类节点的极简联动画布：触发（设备/告警数据）→条件判断→对象查询→动作（派工单/发通知/控设备），部署即生效；zhyq可先用它把'IoT告警→自动生成物业工单并按空间派单'做成第一条真实联动规则，替代现在的模拟对接
- **[D2流程编排]** 借鉴'指标编排发布为API+资源目录授权'模式：把财务报表和驾驶舱指标抽象成 原子指标（账单/收款按日聚合）→衍生指标（回款率/坪效）的指标定义表，驾驶舱和/screen大屏统一消费指标API，不再每张报表各写一套查询
- **[D4架构设计]** 第三方对接从'模拟'升级为微瓴式连接器层：先定义标准对象模型（电表/门禁/停车道闸的公共模型+项目自定义字段），对接适配器只负责把厂商协议翻译成模型上报，业务模块只读模型不碰厂商API，将来换真设备零改动
- **[D1功能分类]** 引入微瓴的空间编码体系：给楼宇→楼层→房源→点位一套带层级语义的统一编码（类POIID），让工单、能耗、设备告警、合同租控都挂到同一棵空间树上，实现'点一个房间看到它的租约+账单+工单+设备'
- **[D3前端体验]** 把/screen大屏模板化：参照IOC主题模板思路做招商/能耗/安防/物业4套可配置大屏主题，各主题由同一套指标API驱动、JSON配置卡片布局，新园区上线大屏从定制开发变成选模板+勾指标
