## 1. 目标与非目标

**目标**：配置化的「触发→条件→动作」规则表，把散落的事件联动收敛成一张可配置规则。首条规则=**IoT 告警自动生成工单并按空间派单**。

**非目标**：不做规则的可视化编排界面（先用 SQL/接口配规则）；不做复杂表达式引擎（条件用简单 JSON 字段匹配）；不做多动作编排（一规则一动作，多动作后续扩展）。

## 2. 现状锚点（探查确认）

- `DomainEvent.AlarmRaised(alarmId, deviceId, level, spaceId, occurredAt)` record 已存在（批次① 占位），**零发布点**。
- `AlarmController.add()` 裸 `alarmMapper.insert()`，未发事件。
- 现有监听器模式：`@TransactionalEventListener(phase=AFTER_COMMIT, fallbackExecution=true)`（见 TodoEventListener / WorkflowCallbackListener）。
- `WorkOrderController.add()` 创建工单并发 `WorkOrderCreated` 事件——可复制此路径创建规则动作产出的工单。
- **⚠️ 前置缺口**：`iot_device`/`pm_work_order` 表有 `space_id` 列（V19），但 `Device`/`WorkOrder` 实体未映射 `spaceId` 字段——本任务须补。
- 下一个空 Flyway = **V22**。类名 Rule/RuleEngine 无冲突。

## 3. 表结构（Flyway V22）

### sys_rule（联动规则）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | |
| name | varchar(64) | 规则名 |
| trigger_type | varchar(32) | 触发事件类型，首期 `ALARM_RAISED` |
| condition_json | varchar(512) | 条件（JSON），如 `{"minLevel":2,"deviceType":"fire"}`；空=无条件全匹配 |
| action_type | varchar(32) | 动作类型，首期 `CREATE_WORKORDER` |
| action_config_json | varchar(512) | 动作配置（JSON），如 `{"orderType":"repair","title":"告警工单"}` |
| priority | int | 多规则匹配时执行顺序（小先） |
| enabled | tinyint | 1启用 0停用 |
| （BaseEntity） | | |

索引：`idx_trigger (trigger_type, enabled)`。V22 附带**一条种子规则**（ALARM_RAISED→CREATE_WORKORDER，无条件）。

## 4. 组件

- **实体字段补齐**：`Device` + `Long spaceId`；`WorkOrder` + `Long spaceId`（表列已存在，仅加字段+让 MyBatis-Plus 映射）。
- **发布点**：`AlarmController.add()` 插入成功后，发 `AlarmRaised(alarmId, deviceId, level, device.spaceId, now)`（level 取告警级别；spaceId 取自 device）。用现有 `ApplicationEventPublisher` + AFTER_COMMIT 模式（与 ContractService.approve 发事件一致）。
- **RuleEngine**（`com.zhyq.park.rule`，新模块）：
  - `RuleEngineListener`：`@TransactionalEventListener(AFTER_COMMIT, fallbackExecution=true)` 消费 `AlarmRaised` → 查 `sys_rule` where trigger_type=ALARM_RAISED and enabled=1 order by priority → 逐条 `RuleEvaluator.matches(rule, event)` → 命中则 `RuleActionExecutor.execute(rule, event)`。
  - `RuleEvaluator`：解析 condition_json，对事件字段做简单匹配（minLevel≤event.level、deviceType 等）。纯函数，**含 JUnit**。
  - `RuleActionExecutor`：action_type=CREATE_WORKORDER → 按 action_config + event 组装并插入 `pm_work_order`（spaceId=event.spaceId，实现"按空间派单"的空间归属；owner/派单人暂占位 system——#7 后接真实），发 `WorkOrderCreated`。
  - `Rule` 实体 + `RuleMapper`（放 `com.zhyq.park.rule.mapper`）。
- **RuleController**（`/rule`）：规则 CRUD（list/get/add/update/delete/toggle）——运维配规则用。

## 5. 防重/幂等 & 零触碰

- 告警自动生成工单要防刷屏：#13 会给 alarm 加唯一约束（本任务先不做去重，#13 补）；本任务规则动作创建工单前**按 (源告警id, 规则id) 查重**，同一告警同一规则不重复建单——工单加 `source_alarm_id bigint null` 列（V22 一并加），防重查它。
- 零触碰：AlarmController 只在 insert 后追加发事件（try 包裹，发事件失败不影响告警落库）；不改告警既有字段/查询。WorkOrder 只加 spaceId + source_alarm_id 两列，既有逻辑不动。

## 6. 决策（本轮自主定，YAGNI）

- D1 条件引擎：简单 JSON 字段匹配（非表达式引擎）。
- D2 动作：一规则一动作，首期仅 CREATE_WORKORDER。
- D3 派单人：占位 system（#7 后接真实指派）。
- D4 防重：工单加 source_alarm_id，(alarm,rule) 维度防重。
