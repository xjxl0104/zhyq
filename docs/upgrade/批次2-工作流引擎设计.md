# 批次② 工作流引擎设计（轻量自建审批链）· 待审阅

> 版本 v0.1（2026-07-13）· 状态：**待用户审阅**，通过后再派 Opus 编码 + Fable 审查
> 选型已定：轻量自建审批链（非 Flowable）；接口形状按 yudao BpmApi 预留，重场景后续可换引擎
> 约束：本文只做设计，不含代码；编码前此文档需你确认

---

## 1. 目标与非目标

**目标**：把现在"往 `biz_approval` 插一条记录 + 一次性通过/驳回"的伪审批，升级为**可配置多节点审批链**：一个审批单按预定义节点顺序流转，每节点可指派审批人，通过/驳回驱动业务回调（首个场景=合同审批）。

**非目标（本期不做）**：会签/或签的复杂投票、并行网关、BPMN 图形建模、动态表达式引擎。这些是"重场景"，留待确需时换 Flowable。

---

## 2. 现状锚点（来自探查，编码时对齐）

- 现有 `biz_approval` 表被两个实体映射：`contract/entity/ApprovalRef`（无审批人字段）、`oa/entity/Approval`（有 approveBy/approveTime/opinion）。状态：1草稿 2审批中 3通过 4驳回 5撤回 6终止。
- `oa/controller/ApprovalController` 的 `/{id}/approve`、`/{id}/reject` 是**单节点条件更新**，审批人硬编码 "system"；`bizType=contract` 时回调 `contractService.approve(bizId)`。
- 合同提交审批：`ContractService.submit()` 插一条 `ApprovalRef(status=2)`，批次② 已让它发布 `ContractSubmitted` 事件。
- 待办 `sys_todo` 已可承载审批待办（批次② 的 `TodoEventListener` 已接 `ContractSubmitted → 审批待办`）。

## 4. 核心流转逻辑（WorkflowService，单 @Service 类）

沿用项目"条件 UPDATE 抢状态"并发防重手法。

1. **start(bizType, bizId)**：按 bizType 找启用的 definition → 建 wf_instance(current_seq=1, status=审批中) → 为第 1 个节点建 wf_task(status=待审) → 发布 `WorkflowTaskCreated` 事件（→ TodoEventListener 建审批待办）。
2. **approve(taskId, opinion)**：抢 task 状态 待审→通过；判断是否还有下一节点：
   - 有 → instance.current_seq++，为下一节点建 task，发事件建待办；
   - 无（末节点）→ instance.status=通过，发布 `WorkflowApproved(bizType,bizId)` 事件。
3. **reject(taskId, opinion)**：抢 task 待审→驳回 → instance.status=驳回 → 发布 `WorkflowRejected(bizType,bizId)` 事件。
4. **业务回调**：新增监听器消费 `WorkflowApproved`，按 bizType 分发——`contract` → 调 `contractService.approve(bizId)`（**复用现有方法，不改其内部锁房源+生成账单逻辑**）。这样审批链是"叠加在合同审批之上的前置流程"，合同的钱/房逻辑一字不动。

## 5. 与 ContractService 的接入点 & 回退方案（关键，无测试）

**接入方式（低侵入）**：
- 合同提交审批 `submit()`：除现有插 `biz_approval` 外，调 `workflowService.start("contract", id)`。若该 bizType 未配置流程定义，`start()` 直接返回（降级为旧行为），保证**未配流程也能跑**。
- 合同的实际"通过"仍走 `ContractService.approve()`，只是触发方从"人点 ApprovalController.approve"变为"审批链末节点通过后的 `WorkflowApproved` 回调"。

**回退方案（改崩怎么退）**：
1. 流程定义 status=0 停用 → `start()` 降级，系统回到旧的单节点审批，零代码回滚。
2. 新表与 `biz_approval` 解耦（D1-方案A），删除 wf_* 表不影响合同主数据。
3. 编码时 `ContractService.approve()` 本体不动，审批链只是"多包一层"，最坏情况摘掉回调监听器即恢复。
4. 上线前用 Fable 审"审批链→合同approve"的回调路径与事务边界，再放 Opus 动手。

## 6. 待你拍板的决策点

- **D1 单据头归属**：方案A=保留 `biz_approval` 作单据头、wf_* 挂其上（改动最小，推荐）；方案B=wf_instance 自立、`biz_approval` 只读兼容（更干净但要迁移现有查询）。
- **D2 审批人来源**：项目当前无登录鉴权（操作人恒 system）。本期审批人按"角色码/用户名约定值"存，**真实指派与"我的待办"过滤依赖 #7 鉴权轮**。是否接受本期审批人先占位、#7 后补？
- **D3 覆盖场景范围**：首期只做"合同审批"一条链，还是同时铺"合同变更/退租/免滞纳金"四条？（表结构已支持多 bizType，差异只在配置与回调分发）
- **D4 yudao BpmApi 形状**：接口方法名/入参是否严格对齐 yudao（便于将来换 Flowable 少改调用方），还是按本项目习惯命名即可。
