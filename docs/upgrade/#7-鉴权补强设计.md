# #7 鉴权补强设计（Spring Security + BCrypt + 无状态 JWT）· 待审阅

> 版本 v0.1（2026-07-15）· 状态：**待用户审阅**，通过后再派 Opus 编码 + Fable 审查
> 方案已定（用户拍板）：**Security + BCrypt + 无状态 JWT**（access 短 + refresh 长，均无服务端存储）；授权**做到角色级**（@PreAuthorize，复用现有 sys_role），菜单/按钮级细权限（#19）留批次③；旧密码**一次性重置**（迁移脚本）
> 约束：本文只做设计，不含代码；编码前此文档需你确认。项目**无测试**，鉴权是全局横切，改动遵循"响应形状不变、前端零改/微改、可三文件回退"原则。

---

## 1. 目标与非目标

**目标**：把现在"SHA-256(密码+盐) 比对 + 内存 TokenStore（8h、重启失效）+ WebMvc 拦截器只验 token 有效性"的演示级鉴权，升级为**生产可用鉴权**：
- 密码 BCrypt 存储（不可逆、带盐、自适应强度）；
- Spring Security 过滤链 + 无状态 JWT（access + refresh），重启不失效、可水平扩展；
- 授权到**角色级**（@PreAuthorize / hasRole），打通 sys_user→sys_role→权限 的读取通道；
- 顺手兑现调研报告点名的**"审计真实操作人"**——把审计/自动填充里的固定 "system" 换成当前登录用户。

**非目标（本期不做）**：
- 不做菜单级/按钮级细粒度权限（#19，依赖本轮打通的通道，留批次③）；不给 73 个 controller 全量标注 @PreAuthorize（只示范高危端点）。
- 不做服务端令牌撤销/在线用户强制下线（无状态 JWT 的取舍，见 §6，留"token_version"扩展位）。
- 不做租户小程序登录/开放 API 鉴权/免登分享（那些是本轮打好地基后的下游，#22 等批次做）。

## 2. 现状锚点（来自探查，编码时对齐）

- `auth/AuthController`：`/auth/login` 用 `DigestUtil.sha256Hex(password + "zhyq")` 比对 `sys_user.password`；`/auth/logout` 调 TokenStore.revoke。校验 `status==1`。
- `auth/TokenStore`：`ConcurrentHashMap<token, {username, expireAt}>`，TTL 8h，重启清空。
- `auth/AuthInterceptorConfig`：`WebMvcConfigurer` 注册 HandlerInterceptor，`/**` 校验 `Authorization: Bearer`，放行 `/auth/login` + swagger（`/doc.html`、`/webjars/**`、`/v3/api-docs/**`、`/swagger-ui/**`）+ `/error`、`/favicon.ico`。401 返回 `Result.fail(401, "未登录或登录已过期")`。**只验 token、不校验角色/权限**。
- `sys_user`（`@TableName sys_user`）：字段含 username / password（`@JsonProperty WRITE_ONLY` 不外泄）/ nickname / status / userType 等，**无直接 role 字段**。
- 角色关联：`sys_user_role(user_id, role_id)`、`sys_role(code, name, dataScope, status...)`、`sys_role_menu(role_id, menu_id)` 表存在于 V1，但**无对应 Java 实体/Mapper**（需本轮补最小查询）。
- 密码种子（V16）：`admin / zhyq@2026` = `SHA-256("zhyq@2026zhyq")`。SHA-256 单向不可逆，**无法程序化转 BCrypt**，只能重置。
- 审计操作人：`MyMetaObjectHandler` 与批次② 的 `AuditAspect` 目前把操作人固定填 "system"。
- **项目尚未引入 spring-boot-starter-security 依赖。**

## 3. 组件设计

### 3.1 依赖（pom）

- `spring-boot-starter-security`
- `io.jsonwebtoken:jjwt-api / jjwt-impl / jjwt-jackson`（0.12.x）

### 3.2 SecurityConfig（`common/security/SecurityConfig`）

- `SecurityFilterChain`：
  - `sessionManagement` = **STATELESS**；
  - `csrf().disable()`（无状态 + 前后端分离，CORS 已在项目层配置，沿用）；
  - 授权规则：`permitAll` = `/auth/login`、`/auth/refresh`、swagger 那组、`/error`、`/favicon.ico`；`anyRequest().authenticated()`；
  - 注册 `JwtAuthenticationFilter` 于 `UsernamePasswordAuthenticationFilter` 之前；
  - `exceptionHandling`：未认证 → 401、无权限 → 403，**响应体统一走 `Result.fail(...)`**（自定义 `AuthenticationEntryPoint` + `AccessDeniedHandler`，保持与现有 `{code,msg,data}` 形状一致，前端 axios 拦截器无需改）。
- `@EnableMethodSecurity`（开启 @PreAuthorize）。
- Beans：`PasswordEncoder` = `BCryptPasswordEncoder`；`AuthenticationManager`（暴露供 AuthController 用）。

### 3.3 JwtService（`common/security/JwtService`）

- 签发 **两枚无状态 JWT**：
  - **access**：TTL 短（默认 **2h**），claims = `sub=username`、`uid`、`roles`（角色码列表）；
  - **refresh**：TTL 长（默认 **7d**），claims = `sub=username`、`type=refresh`；
- HS256，密钥从 `application.yml` 的 `jwt.secret` 读（走环境变量占位 `JWT_SECRET`，与项目 DB_URL 等既有占位风格一致；本地默认值保留）；
- 方法：`generateAccess(user, roles)`、`generateRefresh(user)`、`parse(token)`（验签+过期→claims，失败抛特定异常）。

### 3.4 JwtAuthenticationFilter（`common/security/JwtAuthenticationFilter`，OncePerRequestFilter）

- 取 `Authorization: Bearer`，无则放行给后续（由 SecurityConfig 的 authenticated 规则拒 401）；
- 有则 `JwtService.parse`：成功 → 用 claims 里的 `roles` 构造 `List<SimpleGrantedAuthority("ROLE_"+code)>`，塞 `UsernamePasswordAuthenticationToken` 进 `SecurityContextHolder`；`uid/username` 存入 principal 供审计取用；
- 解析失败/过期 → 不塞 context（交给 EntryPoint 出 401），**access 过期时前端凭 refresh 换新**（见 §4）。

> 设计选择：roles 直接放进 access token 的 claims，过滤器不查库即可鉴权（无状态本意）。角色变更在 access TTL（2h）内有延迟——可接受；要即时可让用户重登。

### 3.5 UserDetailsServiceImpl（`common/security/UserDetailsServiceImpl`）

- 仅**登录时**用（换 access 时不查库，靠 refresh claims）：按 username 查 `sys_user`（校验 status==1）→ 查 `sys_user_role` join `sys_role` 得角色码列表 → 组 UserDetails（含 uid、加密密码、authorities）。
- 需补最小查询：`SysUserRoleMapper`（放 `system/mapper`，`@TableName sys_user_role` 或直接 `@Select` 联表查角色码）。**放对包**（`*.mapper`），避免批次② 那种运行期扫描崩溃。

### 3.6 AuthController 重写（`auth/AuthController`）

| 接口 | 行为 |
|---|---|
| `POST /auth/login` | 用 `AuthenticationManager.authenticate`（内部走 UserDetailsService + BCrypt 校验）→ 成功签发 **access + refresh**，返回 `{token(=access), refreshToken, username, nickname, roles}`（token 字段名保留，前端存取无需改） |
| `POST /auth/refresh` | 入参 refreshToken → 校验 type=refresh 且未过期 → 重查角色（或用 refresh 内 uid 轻查）→ 签发新 access（可选滚动刷新 refresh） |
| `POST /auth/logout` | 无状态：**前端弃 token 即可**，服务端 no-op（保留接口，返回 ok，避免前端 404） |
| `GET /auth/me` | 从 SecurityContext 返回当前用户信息（前端刷新页面恢复登录态用） |

- 删除 `auth/TokenStore` 与 `auth/AuthInterceptorConfig`（Security 过滤链接管全局鉴权）。

### 3.7 授权标注（角色级，本期只示范）

- 打通通道后，给**少数高危端点**加 `@PreAuthorize`，作为范式样例（不铺全量）：
  - 合同：`ContractController` 的 approve / terminate；
  - 财务：`finance` 的收款/发票关键写操作；
  - 系统管理：`SysUser` / `SysRole` 的增删改。
- 用 `hasRole('ADMIN')` 或 `hasAnyRole(...)`（角色码对齐 sys_role.code 种子）。#19 批次再把 sys_menu.perms 串成细权限、逐 controller 铺开。

### 3.8 审计真实操作人（顺手兑现，低成本高收益）

- 新增 `SecurityUtils.currentUsername()` / `currentUid()`：从 `SecurityContextHolder` 取。
- `MyMetaObjectHandler`（create_by/update_by 自动填充）与批次② `AuditAspect`（操作人）从固定 "system" 改为 `SecurityUtils.currentUsername()`，取不到时（如系统任务/未登录上下文）回退 "system"。
- 这直接兑现调研报告 §横切前置 点名的"审计真实操作人"，且不引额外表。

## 4. 前端影响（微改，非零改）

- **登录响应**：多返回 `refreshToken` + `roles`；`token` 字段名不变，现有 `Authorization: Bearer` 存取逻辑不动。
- **401 处理**：现有 axios 响应拦截器遇 401 已有跳登录逻辑；建议增强为"先拿 refreshToken 静默换 access、失败再跳登录"（提升体验，可选，不做也能跑）。
- **响应体形状不变**：401/403 仍是 `{code,msg,data}`，前端错误提示逻辑无需改。
- 结论：前端**最小改动 = 登录时多存一个 refreshToken**；静默刷新是可选增强。

## 5. 密码迁移（一次性重置，Flyway V20）——⚠️ 破坏性操作

> SHA-256 单向不可逆，**无法把老哈希转成 BCrypt**，只能重置。用户已确认"一次性重置"。

- **做法**：Flyway `V20__auth_bcrypt_reset.sql` 写入**预计算好的 BCrypt 字面量哈希**（编码阶段用 BCryptPasswordEncoder 离线算好，直接写进 SQL，不在运行期算）：
  - `admin` → `BCrypt("zhyq@2026")`：**保持原口令可登录**，验收账号不变。
  - 其余种子用户 → 统一重置为**文档记录的默认口令**（如 `Zhyq@2026`），并在 §7 / DEPLOY 文档列明，要求首次登录后改密。
- **⚠️ 影响与告知**：
  - 该迁移执行后，除 admin 外所有既有用户的旧密码失效，须用新默认口令登录。
  - 生产库若已有真实用户密码，**上线前必须与用户确认名单与通知方式**（本项目当前为演示库，主要影响种子账号）。
  - 迁移**不可回退**（重置后无法还原原哈希）——这是本设计里唯一不可逆步骤，与 #3 的纯叠加不同。

## 6. 无状态的取舍 & 回退方案（关键，无测试）

**无状态 JWT 的已知代价（如实标注）**：
- 登出 / 改密 / 禁用用户**不能主动踢人**——已签发的 access 在 TTL（2h）内仍有效。
- 缓解：access TTL 压到 2h + refresh 轮换；高危操作（改密后）提示用户"其他设备最多 2h 后失效"。
- **未来扩展位（本期不实做，只留设计）**：给 `sys_user` 加 `token_version int` 列，签发时写入 access claims，过滤器校验时比对当前值；改密/禁用时 `token_version+1` 即令旧 token 失效。这是"软撤销"的最便宜实现，无需 session 存储；确需即时踢人时再启用。

**回退方案（改崩怎么退）**：
1. 鉴权链回退 = 还原 **三文件**：删掉 `common/security/*` + 恢复 `auth/TokenStore` + `auth/AuthInterceptorConfig` + `AuthController` 旧版；pom 移除 security/jjwt 依赖。因新旧都走 `Authorization: Bearer` + `Result` 响应形状，前端无需回退。
2. `@PreAuthorize` 标注是加法，去掉注解即回到"只认证不授权"。
3. 审计操作人改动可独立回退（改回固定 "system"）。
4. **密码重置（V20）不可回退**——若要回退鉴权又想恢复旧登录，需重新灌 V16 种子哈希。**建议 V20 上线前单独确认。**
5. 上线前用 Fable 审：过滤链顺序 / permitAll 清单是否遗漏（尤其 swagger、health）、JWT 验签与过期边界、密码迁移 SQL 的哈希正确性、@PreAuthorize 是否误伤放行端点。

## 7. 待你拍板的决策点

- **D1 access / refresh TTL**：access 2h + refresh 7d（推荐）？还是更短的 access（如 30min）更安全但刷新更频繁？
- **D2 非 admin 种子账号默认口令**：统一重置为 `Zhyq@2026`（推荐，文档列明）还是逐个指定？admin 保持 `zhyq@2026` 不变已定。
- **D3 @PreAuthorize 示范范围**：就示范 合同approve/terminate + finance关键写 + 系统用户/角色管理（推荐），还是本轮多铺一些？角色码需对齐 sys_role 种子（编码时确认现有种子角色码，如 ADMIN/OPERATOR…）。
- **D4 静默刷新前端增强**：本轮一并做（401→用 refresh 换 access 再重试），还是先只做后端、前端仅存 refreshToken、静默刷新留后续？
- **D5 swagger 在生产是否放行**：现拦截器放行 swagger 方便看接口；生产是否收紧为需登录/关闭？（可用 profile 区分）
