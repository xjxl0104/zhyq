## 1. 流程能力差距分析（四大能力）

### 1.1 审批流引擎

**对标产品的两条路线**：

- **通用 BPM 路线**（业务后台系）：
  - **yudao**：Flowable 6.8 + 双设计器（仿钉钉 SIMPLE 覆盖 80% 场景 / BPMN 兜底），会签/或签/依次、驳回/转办/委派/加签、超时审批与自动提醒、表单字段级权限；最关键的是「**业务表单**」接入模式——业务表加 `process_instance_id + status` 两字段，经 `BpmProcessInstanceApi` 发起，终态由事件监听器回调业务（合同审批通过→回调里执行生成账单+锁房源），业务与引擎解耦。
  - **JeecgBoot**：同为 Flowable，核心设计是「流程与表单分离 + 表单挂靠」，节点可挂 Online 表单/设计器表单/手写编码表单三类，业务逻辑经任务扩展接口注入（注意：完整流程设计器属商业版）。
  - **IBM TRIRIGA**：国际 IWMS 范式——每个业务对象定义 State Transition Family（状态转移族），表单按钮/系统事件触发工作流，审批用「分发列表」会签，通知集中配置；产品交付的默认流程客户可用同一套 Workflow Builder 改造。
  - **明源云**：审批流不内嵌业务模块，由天际流程平台（bpmPaaS）统一承接，对业务开放 81 个 API + 65 个流程事件，「合同审批通过事件」触发生成账单等后续动作——事件订阅替代硬编码。
  - **Yardi**：审批内建于核心（非独立 BPM）：PayScan 发票按「角色+金额限额」路由，Workflow Dashboard 集中待办，退回必填原因、审批历史留痕（SOX 合规）。
  - **Odoo**：最轻做法——Studio Approval Rules 把多级审批挂在**表单按钮**上（条件表达式、顺序步骤、同人互斥、未授权点击自动生成待办、记录写入 chatter），一张 approval_rule 表 + 按钮拦截即可落地。
- **不做通用 BPM 路线**（楼宇/IoT 系）：Siemens Building X、JCI OpenBlue、Honeywell Forge、腾讯微瓴、OfficeRnD/Nexudus 均**没有**通用审批引擎，审批以场景化开关实现（预订需审批、prorated 发票需审批），复杂编排交给规则引擎/外部工具——证明「先可配置审批链、后全量 BPMN」是被验证的渐进路径。

**zhyq 现状：没有。** 差距细分：
1. 无可视化流程定义（谁审、几级、什么条件走哪条分支）——出处：yudao/JeecgBoot/TRIRIGA/明源；
2. 无通用审批动作集（会签/或签/驳回/转办/加签/撤销）——出处：yudao/TRIRIGA；
3. 审批与业务耦合（状态流转直接写业务表，无事件回调位）——出处：yudao 业务表单模式/明源流程事件；
4. 无审批留痕与退回原因必填——出处：Yardi/Odoo chatter；
5. 统一待办已有（**部分有**），但只是列表聚合，缺「待办→审批动作→下一步」的处置闭环页——出处：Yardi Workflow Dashboard、yudao 审批中心。

### 1.2 跨模块联动编排（事件—规则—动作）

**对标成熟做法**（这是园区类产品流程编排的主战场）：

- **华为 ROMA/IOC**：「子系统事件→平台规则/预案→跨系统动作序列」三件套：LINK 规则引擎（阈值/时间/空间维度触发）+ ROMA 业务流低代码编排 + IOC 预案引擎（预案=步骤模板，一键启动、逐步联动、全程留痕；中海物业事件响应 7.5 分钟→2 分钟）。
- **腾讯微瓴**：画布式零码编排，仅四类节点——**触发**（查询设备影子）→**条件**（逻辑判断）→**对象查询**（空间语义找附近设备）→**动作**（设备控制/派单），连线后「部署即生效」；另有「指标编排发布为 API + 资源目录授权」。
- **海康 iPark**：**事件中心**是全平台流程枢纽——任何子系统事件按「事件类型」配置一条处置链：启用状态→事件等级→关联标签→关联预案→关联工单→处置→归档，预案有统一模板库；替代各模块各写状态机。
- **阿里云园区引擎**：统一事件模型（车/人/周界/消防/能效/环境）→联动规则→自动生成工单→统一推送到人（钉钉触达）；SaaS 经 AMQP 订阅事件而非轮询。
- **ThingsBoard**：规则链有向图（Filter/Enrichment/Action/External 节点），Create Alarm/Clear Alarm/发邮件/调 REST 都是标准节点——「遥测→判断→告警→通知→反控」闭环的开源实现范本。
- **Siemens Building X**：FDD 400+ 预置规则 → 事件自动建工单 → 工单状态回写关闭事件；通知规则（事件类型+范围+接收人+渠道）是**用户可配置的数据而非代码**。
- **新华三绿洲**：「报警引擎→工单引擎」范式（生态七引擎）；特斯联：TCA 式「触发-条件-动作」+ 火灾应急「事件→态势推演→多系统动作」。

**zhyq 现状：没有。** 唯一联动（合同→账单+锁房源）为硬编码；告警→工单、能耗超标→通知、合同到期→跟进 等联动全部缺失或靠人肉。差距本质：**缺一张「触发条件（事件类型/阈值/空间/时间）→动作（建工单/发通知/改状态/调接口）」的规则表和一个统一事件模型**，而不是缺一个重型编排平台。

### 1.3 SLA / 超时升级（工单）

**对标成熟做法**：

- **IBM TRIRIGA**：Request Class（请求分类字典）挂 Service Plan，自动路由到服务方并生成带 SLA 的 Work Task；完工后按配置自动推送满意度回访（Response Log）。
- **Honeywell Forge PdM**（最完整的工单治理样板）：① 动态优先级——每 8 小时按「案件状态×故障持续/复发×预估成本×资产/空间优先级」重算 Priority Score，久未复发自动衰减；② SLA 双档——按优先级配置 Resolution Target（应结天数）+ At Risk（风险预警天数），仪表盘跟踪 MTTC；③ 自动关单——故障恢复 N 天自动关闭；④ 关单治理——必填标准化解决码（30+ 项）与根因码（22 项），沉淀结构化维保知识。
- **openMAINT**：纠正性维护全链路——多渠道报障→服务台审核签报→按故障类型+在约合同**自动建议承修方**→一修可拆多张子工单（各自优先级/技能团队）→工时材料计价入预算科目→领料扣库存→**SLA 超时自动邮件告警**→审批核算关单。
- **MicroCommunity**（同领域开源）：派单三模式（客服手工/师傅抢单/系统轮询自动派单）+ 工单池 + 转单/退回 + 业主评价 + 客服回访满意度。
- **蘑菇物联**：「工单八步走」+ 电子服务工单 + 电子签名 + 客户评价收尾，维保闭环直接支撑维保收费。
- **Schneider EBO**（告警侧同构）：告警生命周期「触发→自动分派到人/组→确认（认领）→复位→关闭」，确认策略按类型三档可配，处理必填「用户操作」备注。

**zhyq 现状：部分有。** 已有全流程状态机 + SLA 字段 + 时间线（在同档产品中不算差）；差距：
1. SLA 只是记录，**无超时自动升级/催办动作**（超时→通知主管/提升优先级/转派）——出处：openMAINT/Honeywell/TRIRIGA；
2. 无派单策略（仅手工派单，无抢单/轮询/按分类自动路由）——出处：MicroCommunity/TRIRIGA；
3. 无回访评价环节（验收即结束）——出处：TRIRIGA/MicroCommunity/蘑菇；
4. 无标准化关单码/根因码，报表无从沉淀——出处：Honeywell；
5. 优先级为静态人工字段——出处：Honeywell 动态评分（P2 级借鉴）。

### 1.4 自动化触发（合同→账单→收款→收据 主链）

**对标成熟做法**：

- **明源云**（与 zhyq 主链最贴）：财务闭环拆「**出账—催账—核账—做账**」四段全在线：计费引擎按合同批量出账（10000+ 算费场景）→一键催缴联动租户小程序缴费→收款自动核销→开票→对接做账；且以「**预警驱动业务**」串联模块——空置/到期/欠费预警统一成预警中心，每条预警一键转招商跟进/续租商机/催缴任务。
- **Odoo**：账单**滚动生成**而非一次性生成全部周期——合同维护 `next_invoice_date`，每日 cron 到期才生成并顺延；「Contract in exception」异常标记阻断自动扣款防重复；欠费 N 天 Automatic Closing 自动关约；逾期罚金（Extra Days）与两次租赁间锁资源（Padding Time）均为可配置参数而非硬编码。
- **OfficeRnD/Nexudus**：合同签署（电子签回调）即在**一个事务内**自动生成周期账单计划+资源占用+锁定平面图房源，且**前置校验资源可用性冲突（冲突则阻止合同生效）**；billing day 自动 Bill Run 归集会员费+预订费+散单；到期自动催缴、逾期费、超期自动暂停服务；所有变更外溢 Webhook 供门禁/WiFi 联动。
- **Yardi**：租约条款自动生成周期 charge；滞纳金按规则自动评估；逾期率设阈值越界自动告警；**CAM 年度对账闭环**（费用池→pro-rata 月度预估→年终对账→差额自动补收/退款→重算次年预估）；租户门户余额与 AR 完全同源，收款自动过账。
- **JCI OpenBlue**：租户能耗计费闭环——表计→费率卡→多表分摊→账单**人工审核**→批量发送→租户门户自助查账，跨「空间+设备+财务」三域。
- **MicroCommunity**：定时任务自动出账、公众号欠费模板消息催缴、微信线上退费、租金按年自动递增、间歇性费用。

**zhyq 现状：部分有。** 主链「合同审批→自动生成周期账单+锁房源→收款幂等→滞纳金→收据」已成形（这是 zhyq 的灵魂资产，同档开源项目里仅 ics-park 可比）。差距：
1. **催缴环节断链**：逾期账单只有列表（Overdue.vue），无「欠费预警→催缴任务→通知渠道→缴后自动销task」流水线——出处：明源/Yardi/Nexudus/MicroCommunity；**没有**；
2. **无预警驱动机制**：空置、合同到期、欠费三大预警各自为政或缺失，不能一键转业务动作——出处：明源；**没有**；
3. 账单一次性全量生成，中途调租/退租需手工改账单，无滚动生成与 exception 阻断——出处：Odoo；**部分有**（能生成但不灵活）；
4. 无电子签集成位与合同生效前资源冲突校验（zhyq 锁房源发生在审批后，无前置冲突拦截）——出处：OfficeRnD/明源/Odoo Sign；**没有**；
5. 无租户自助缴费/对账触点，催缴通知无真实出口（短信/支付全模拟）——出处：Yardi CommercialCafe/明源小程序；**没有**（归属 D1/D3 补齐，此处只记流程依赖）；
6. 无公摊/能耗分摊类费用的「预估—实缴—对账」流程——出处：Yardi CAM/TRIRIGA OPEX/JCI Tenant Billing；**没有**。

## 2. zhyq 主链路逐段对照（招商→合同→财务→物业→能耗→IoT）

### 2.1 招商 → 合同

| 对标成熟做法 | 出处 |
|---|---|
| 「线索—商机—签约」漏斗，商机沉淀跟进记录/历史报价/意向书附件，支持多客商比价 | 明源云（七环节漏斗）、yudao CRM（线索-公海超期回收-商机-合同-回款） |
| 交易里程碑管道（报价已发/LOI 签署/审批通过），成交后一键把客户+房源+商务条款带入合同草稿；**到期租约反向生成续租商机** | Yardi Deal Manager↔Voyager 双向同步 |
| CRM 看板阶段可挂自动动作（跟进提醒/带看提醒/自动邮件），报价+电子签在线完成即转合同 | Nexudus CRM Boards |
| 意向合同实体衔接线索转化与正式合同 | ics-park（意向合同→正式合同→审批） |

**zhyq 现状**：线索公海/认领/跟进/转化**已有**；佣金、渠道页已有。差距：① 无商机/意向合同实体，线索转化到合同起草是**手工断点**（**没有**）；② 无「合同到期→自动生成续租跟进」反向触发（**没有**）；③ 公海无超期自动回收规则（**部分有**——有公海无自动回收，出处 yudao）。

### 2.2 合同段（生命周期）

| 对标成熟做法 | 出处 |
|---|---|
| 租约摘要审批→自动生成租约→激活自动生成付款计划；条款/期权/关键日期结构化，触发到期提醒与续约评估 | IBM TRIRIGA |
| 合同签署事务内：生成账单计划+资源占用+锁房源，**前置资源冲突校验**，电子签回调驱动 | OfficeRnD/Nexudus |
| 5 大要素标准合同模板、在线签约、计费方案挂接、价格变动跟踪、合同变更/续租/退租同一履约线 | 明源云 |
| 合同变更/退租走审批：退租审批联动解锁房源+账单结清校验 | ics-park、明源 |

**zhyq 现状**：合同全生命周期 + 审批通过自动生成账单锁房源 + 退租释放房源留痕**已有**（主干成形）。差距：① 条款/免租期/递增/续约选择权未结构化，无「到期前 N 天自动生成待办」提醒引擎（**部分有**——免租期/保证金支持已有，提醒没有）；② 合同变更/退租无审批流（**没有**，退租直接操作）；③ 无电子签位（**没有**）；④ 租金按年递增等条款自动化（出处 MicroCommunity/Yardi 递增规则）**没有**。

### 2.3 财务段（账单→收款→收据）

见 1.4。补充对照：

| 对标成熟做法 | 出处 |
|---|---|
| 出账-催账-核账-做账四段流水线，回款周期 2.5 天（厂商宣称） | 明源云 |
| 收款按账单自动核销、门户余额=应收余额同源 | Yardi |
| Bill Run 归集多来源费用（租金+预订费+商城散单）为一张发票 | OfficeRnD/Nexudus |
| 逾期率阈值告警（组合/单项目越界即通知） | Yardi |

**zhyq 现状**：账单/收款幂等/滞纳金/收据/发票/收缴率报表**已有**；催缴任务流、自动核销规则、逾期率阈值告警、多来源费用归集（会议室费用、能耗费用并入账单）**没有**。

### 2.4 物业段（工单/会议室/巡更三检/访客）

工单差距见 1.3。补充：

| 对标成熟做法 | 出处 |
|---|---|
| 会议室 Booking Policy 挂在资源上：最长时长/缓冲期/提前窗口/需审批（Tentative+超时未批自动取消）/未签到自动释放；Booking Credits 额度与账单打通 | OfficeRnD |
| 会前自动启动空调灯光（预订事件驱动设备）、会后资源自动释放+纪要整理 | 华为 WeLink、H3C |

### AI 扩展点预留（仅接口位，不展开方案）

- **联动规则中心（P0-1）的动作类型预留 `AI_SUGGEST` 钩子**：规则命中后可调用外部 agent 接口返回处置建议（参考 JCI Performance Advisor「建议流可转工单」、Honeywell Triage 面板内嵌 AI Insights 的嵌入位形态）。
- **工单派单（P1-7）预留智能派单接口位**；**告警模块预留告警归并/降噪接口位**（参考微瓴告警收敛）；**催缴/能耗报告预留自动生成报告接口位**（参考蘑菇「3 秒诊断报告」）。均只定 API 签名与挂载点，不做实现。

### 与其他章节的边界备注

- 租户自助端（缴费/报修/对账小程序）是本章多条流程（催缴、回访、访客）的触达载体，功能本体归 **D1 功能广度**；本章仅声明依赖。
- 事件/告警在大屏上的处置交互（点位下钻、一键派单）归 **D3 前端专题**；统一空间树、第三方适配器层（门禁/支付/短信真实对接）归 **D4 架构设计**。P0-1 事件模型设计时需与 D4 的适配层对齐。
