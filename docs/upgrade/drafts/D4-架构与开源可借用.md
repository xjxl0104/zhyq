# D4 · 架构与功能设计差距 + 开源可借用清单（章草稿）

> 依据：25 张对标卡片（cards/01~25）+ zhyq 现状基线（backend 14 模块 / 前端 14 一级导航 + /screen；第三方对接全模拟；无审批流引擎；表带 tenant_id 但无租户管理）。
> 边界：只谈模块边界、扩展点、对接层与组织方式的**设计**，不涉及后端数据并行处理/存储/中间件实现；AI 仅以「扩展点预留」形式出现，不展开方案。
> 标注约定：每条注明【出处】（哪些对标对象有此做法）与【zhyq 现状】（已有 / 部分有 / 没有）。

## 4.1 架构设计差距

### 4.1.1 第三方对接层：从「全模拟散落各模块」到「标准模型 + 适配器/连接器」

这是本章最大的差距，也是所有头部平台架构上的共同点——**业务模块从不直接面对厂商 API，中间永远隔一层标准模型**：

| 对标做法 | 要点 |
|---|---|
| 腾讯微瓴「对象模型 + 设备影子」 | 公共对象模型 + 项目自定义模型（customModelId）做语义标准化；设备影子（desired/reported）做异步控制闭环；业务系统数据走独立接入通道 |
| 华为 ROMA 四组件 | LINK（设备）/ FDI（数据）/ MQS（消息）/ APIC（API）各管一类集成，**以配置而非改代码对接既有系统**，屏蔽子系统接口差异 |
| 阿里云园区引擎「模板模型 + 适配器应用」 | 先定义设备物模型与子系统应用模型，厂商差异封装在独立适配器里，ISV 只面向抽象模型开发，一次开发多项目复用 |
| Schneider EWS / SmartConnector | 第三方系统经可插拔 Processor 映射为标准 Interface 对象，注册后外部点位/告警即被当作本系统对象托管 |
| H3C 绿洲融合集成平台 | 「非侵入式集成」，协议适配 + 物模型 + 事件标准化，自己只做接入/数据/开发三层 |
| JeecgBoot starter 机制 | jeecg-boot-starter 把外部能力做成按需引入的 starter；system-api 拆 local-api/cloud-api 两实现同接口可切换 |

【zhyq 现状】没有。支付/短信/签章/门禁/IoT 厂商对接全为模拟代码，且直接写在各业务模块内，将来接真设备/真通道时每处都要改业务代码。

**目标形态（建议）**：新增 `integration` 模块（或 backend 内独立包），分两类连接器接口位：
- **设备类连接器**（门禁、停车道闸、电表水表、传感器）：为每类设备定义标准数据模型（上行事件 + 下行控制两向），厂商差异在 `XxxConnector` 实现类里；现有模拟代码降级为 `MockXxxConnector` 默认实现——**模拟与真实同接口，可配置切换**（对齐阿里适配器 + JeecgBoot local/cloud-api 的做法）。
- **服务类连接器**（支付、短信、电子签章）：同样接口 + Mock 实现起步；支付回调、签章回调统一走连接器层进领域事件（见 4.1.3），不直接调业务 Service。

这一层同时是补齐停车/门禁等空白模块的前置件：先出模型接口，再接真设备（海康 Artemis AK/SK + 事件订阅回调可作第一个真实对接场景）。

### 4.1.2 统一空间树与主数据：全系统缺一根「骨架」

【出处】微瓴统一编码体系（wId/POIID/poiCode，一切 API 围绕空间层级查询）；海康「统一资源模型 + 一处录入多处使用」（人/组织/区域/车辆统一建模，LDAP 树形资源目录）；阿里空间中心（空间树为贯穿性主数据，设备/资产/孪生全挂树）；OpenBlue Brick 式空间树（portfolio→location→building→floor→wing→room→asset，权限做到角色+空间级）；Honeywell 空间模型（spatial filter 全仪表盘共用，空间/资产带优先级属性）；openMAINT 空间层级（建筑群→楼→层→房间，设施系统与空间分离）。

【zhyq 现状】部分有。building 模块已有「项目-楼宇-楼层-房间」树，但：能耗表计、IoT 设备、工单、合同各自维护位置字段，未统一挂树；无统一空间编码；权限与空间无关；无「点一个房间看到它的租约+账单+工单+设备」的聚合能力。

**差距**：空间树未升格为全局主数据服务。建议给楼宇→楼层→房源→点位一套带层级语义的统一编码（类 POIID），合同、账单、工单、能耗点位、设备告警全部引用同一空间节点 ID；大屏与驾驶舱按空间下钻即天然聚合。这也是将来资产管理模块（华为资产全生命周期 / Snipe-IT 六类对象）的载体，并为「角色+空间节点」两维权限预留粒度。

### 4.1.3 统一事件中心与开放事件（Webhook）：跨模块联动的架构位

【出处】海康「事件中心」（任何子系统事件先进事件中心，按事件类型配置 等级→标签→预案→工单 的处置链；对外 eventSubscriptionByEventTypes 回调推送）；阿里园区引擎「事件-联动-工单」闭环 + AMQP 事件订阅（SaaS 靠订阅事件联动而非轮询）；OfficeRnD/Nexudus 的领域事件 Webhook（contract signed / invoice generated 等，HMAC-SHA256 签名，后台自助配置 Endpoint，官方明确「不建议轮询」）；明源云天际流程平台对业务开放 81 API + 65 流程事件；Honeywell 官方连接器以 webhook 订阅工单 + 关单 API 对外编排；微瓴以 message_type 做应用间路由解耦。

【zhyq 现状】没有。跨模块联动（合同审批过→生成账单+锁房源）是 Service 内硬编码；告警与工单是两个孤岛；对外没有任何事件出口。

**差距**：缺一个「领域事件」抽象位。建议最小集约 10 个事件（合同签署/审批通过、账单生成、收款到账、工单创建/关闭、告警触发/恢复、合同到期预警、退租完成），先做**进程内事件总线**（Spring Event 即可，不涉及消息中间件选型），同时预留对外 Webhook 推送（HMAC 签名 + 后台配置页）。事件中心是 D2 章各类流程闭环（告警→工单、预警驱动业务）的架构承载位，也是 AI 扩展点的主要挂载点（见 4.2）。

### 4.1.4 开放 API 设计：从「有接口文档」到「API 作为产品」

【出处】Siemens Building X（API 与应用同级作为可售产品：8 类 API 产品、OAuth2 Client Credentials + Machine User、JSON:API + OpenAPI 文档 + 沙箱 + 3 个月弃用预告 + 全链路 X-Request-Id）；海康 Artemis 网关（AK/SK 签名 + HTTPS，统一 /artemis/api/... 前缀）；JeecgBoot OpenAPI 模块（接口管理/AK-SK 授权/接口文档）；ThingsBoard REST/WebSocket 全量 API；Honeywell API Marketplace + 开发者沙箱；明源云集成云接口中心统一鉴权。

【zhyq 现状】部分有。Knife4j 已产出 OpenAPI3 文档，但接口无鉴权（演示级）、无对外授权概念、无调用方管理、无 requestId 贯穿。

**差距**：对外集成边界不存在。建议顺序：先补登录鉴权（既有已知空白），再叠加「开放 API 最小集」——机器账号（client_credentials 或 AK/SK）+ 按园区/租户范围授权 + 全链路 requestId + 先开账单/工单/能耗三个域的只读 API（对齐 Building X 的起步建议）。这也是惠企/政务对接与未来 agent 接入的同一个出口。

### 4.1.5 审批流引擎的「位置」：平台层独立模块 + 事件回调，不嵌业务

（流程能力本身归 D2 章，这里只谈架构定位。）

【出处】yudao BPM「业务表单」模式（业务表加 process_instance_id/status 两字段，经 BpmProcessInstanceApi 发起，终态经事件监听器回调业务——业务与引擎解耦）；明源云天际流程平台（BPM 独立于业务模块，对业务开放流程事件）；TRIRIGA 平台级 Workflow Builder（状态转移族挂在任意业务对象上）；Odoo「按钮级审批规则」（不上重型 BPM，approval_rule 表 + 按钮拦截）；Yardi 内建「角色+金额限额」路由 + Workflow Dashboard 集中待办。

【zhyq 现状】没有。合同审批为模块内简单状态流转，每加一种审批就要再写一遍状态机。

**差距（架构角度）**：审批引擎应是**独立平台模块**，业务对象只挂两个字段 + 订阅终态事件；zhyq 现有「审批通过→生成账单+锁房源」的硬编码正好改造为第一个事件回调消费者。选型上轻重两条路：重=引 Flowable（yudao 模式，含双设计器）；轻=Odoo 式按钮级审批规则表。建议先轻后重，接口位按 yudao 的 API 形状预留，将来可替换引擎不动业务。

### 4.1.6 模块边界与契约：controller 直连 mapper 的单体如何长大

【出处】yudao「module-api / module-biz」拆分（模块间只允许依赖对方 api 模块=接口+DTO，pom 注释即可插拔裁剪，同套模块可平移微服务版）；微瓴微服务边界原则（每服务独占端到端场景与自己的数据，靠 API/消息互通）；海康组件化（业务扩展=新增组件，组件独立数据库）；Odoo addon 范式（__manifest__ 声明依赖，装卸即插即用，一个功能点一个小模块——OCA/contract 拆 30+ 细粒度模块）；Siemens「模块边界=订阅边界」。

【zhyq 现状】部分有。后端已按 14 个包划分模块、命名清晰；但 controller 直接注入 mapper、模块间 Java 调用无契约层，合同↔财务↔物业的耦合点散落，新增模块（资产/停车/门禁）没有标准接入路径。

**差距**：不必立即做 yudao 式全量拆分（成本大、单体现阶段够用），但应先立**依赖规则**：跨模块调用一律走对方的 XxxApi 接口类（先以同包接口形式存在），禁止直接注入他模块 mapper；新模块按「entity/mapper/controller[/service] + XxxApi」模板接入。这为 4.1.3 的事件解耦和将来按需拆分留好缝。

### 4.1.7 设备与告警的领域模型：缺「类型级抽象」

【出处】ThingsBoard Device Profile / Asset Profile（一类设备共享传输配置、默认规则链、告警规则；告警 originator+type 唯一、五级 severity、active/cleared × ack/unack 四态、受理人+评论、清除不删除）；微瓴对象模型；阿里物模型；yudao IoT「产品-物模型-场景联动-告警配置」四层；蘑菇物联 APaaS 物模型 + 规则引擎。

【zhyq 现状】部分有。iot 模块有设备与告警平表，但无设备类型抽象（阈值挂在单设备或写死），告警无生命周期/受理人/去重升级概念。

**差距**：引入「设备类型（Profile）」实体，告警规则挂类型而非实例；告警表按 ThingsBoard 领域模型改造（唯一约束防重复刷屏、双维状态、受理人）。这是 D2 告警→工单闭环的模型前提。

### 4.1.8 指标层：报表各写各查询 vs 指标定义统一消费

【出处】微瓴「原子指标→衍生指标→发布为 API→资源目录授权」；蘑菇物联指标加工流水线（原始读数→分时电量/折碳/能效等业务指标）；明源云「一屏一板一讯」共用一套指标口径；OpenBlue 分层 widgets 消费统一数据模型。

【zhyq 现状】部分有。dashboard 模块有聚合接口，但每张报表/每块大屏卡片各写一套查询，口径无定义处。

**差距**：建「指标定义」薄层（指标名/口径/聚合粒度/数据来源），驾驶舱、/screen、各模块首页看板统一走指标 API。**这是本章为 AI 预留的最重要接口位之一**（agent 问数入口，见 4.2）。

### 4.1.9 多租户 / 多园区组织

【出处】yudao SaaS 字段级多租户（tenant_id 透明拼接 + 租户套餐控菜单，framework 层实现业务无感）；ics-park「租户-多园区」两级（分园区配置权限与数据隔离）——与 zhyq 业务模型最同构；ThingsBoard Tenant→Customer 两级原生隔离；OfficeRnD/Nexudus Organization→Location（每场地独立计费主体/税率/模板，报表跨场地汇总）；明源云集团-分公司-多业态「流程/数据/权限三线分级管控」；Siemens Partition + User Group；华为集中+分布式（集团层集中监管、园区层分布运营）。

【zhyq 现状】部分有。核心表已带 tenant_id 字段（BaseEntity 自动填充）但无租户管理/隔离逻辑；building 有「项目」实体≈园区，但用户-园区无授权关系，数据不按园区隔离，报表不能按园区汇总对比。

**差距分两级**：
- **L1 多园区（近期该做的）**：把「项目/园区」升为组织维度——用户可授权到若干园区、列表页默认按园区过滤、驾驶舱支持全集团汇总+单园区下钻（对齐 ics-park 两级模型 + OfficeRnD 场地级配置思路）。
- **L2 SaaS 多租户（远期可选）**：真正启用 tenant_id 隔离 + 租户套餐（yudao 已给出全套免费参考实现），仅当 zhyq 走向多物业公司 SaaS 交付时才值得做。

## 4.2 AI 扩展点预留设计（只定接口位，不做实现）

原则（来自对标共识）：头部产品的 AI 全部**内嵌在既有业务动作旁**（按钮/钩子/事件/建议卡），几乎没有独立"AI 模块"入口——Honeywell 把 "Generate AI Insights" 放在工单 Triage 面板里，OpenBlue 把建议流做成首页待办卡，明源云把 AI 招商员嵌在漏斗最前端，Siemens 把 AI 排程做成建议卡。因此 zhyq 的预留 = **事件挂载点 + API 接口位 + 前端插槽**三类，不新建 AI 业务模块。

建议预留的接口位清单（每条注明将来能挂什么，本轮一律不实现）：

| # | 接口位 | 放在哪 | 依赖的本章条目 | 将来可挂（对标出处） |
|---|---|---|---|---|
| A1 | **统一指标 API** | 4.1.8 指标层，`/api/metrics/{指标名}` 统一出数 | 指标定义层 | agent 问数/自然语言查报表（微瓴指标 API、Nexudus NAI、JeecgBoot Chat2BI） |
| A2 | **工单流转钩子** | 工单创建/派单/关单三处领域事件 + 派单处一个可空的「建议提供者」接口 | 4.1.3 事件中心 | 智能派单、处置建议、根因分析（Honeywell Triage AI、Schneider Building Advisor FDD、蘑菇物联诊断报告） |
| A3 | **统一待办「建议卡」类型** | todo 模块加一种 source=agent 的待办/建议卡类型，可一键转工单/跟进 | 现有 todo 模块 | 建议流首页（OpenBlue Observations & Recommendations、Yardi 阈值告警） |
| A4 | **问答/助手入口** | 前端全局插槽（顶栏按钮位）+ 后端 `/api/agent/chat` 网关占位 | 无 | 园区问答助手（Ant Design Pro v6 chatbot 标配页、pure-admin chatai 模板、特斯联空间智能体） |
| A5 | **告警 enrich 钩子** | 告警入库前的可空处理链（归并/降噪/定级） | 4.1.7 告警模型 | 告警收敛与扰动过滤（微瓴告警收敛、OpenBlue ML 过滤扰动告警） |
| A6 | **附件解析回调** | 合同/票据上传后的可空解析接口（返回结构化字段草稿，人工确认落库） | 无 | 合同条款抽取、票据 OCR（TRIRIGA/Yardi Smart Lease、Odoo IAP OCR、Siemens 发票 AI 提取） |
| A7 | **大屏/报表配置生成位** | 前提是大屏改为 JSON 配置驱动（D3 章），生成入口只是「产出一份配置 JSON」 | D3 大屏配置化 | AI 生成大屏/图表（DataV 7.0 识图生成+对话生成交互、GoView Pro、JeecgBoot AI Skills） |
| A8 | **Agent 基建**：完整 OpenAPI + 机器账号 + （可选）llms.txt/MCP 描述 | 4.1.4 开放 API | 开放 API 治理 | 任何外部 agent 接入（Snipe-IT 自带 CLAUDE.md/llms.txt/社区 MCP Server 的现成实践） |

> 说明：A1~A3 依赖本章 P0/P1 条目，属「顺手预留」几乎零额外成本；A4 是一个前端按钮位+一个空网关路由；A5/A6 是接口签名上留一个可空扩展点。全部不做实现方案。

## 4.4 章内升级建议清单（价值×成本 + P0/P1/P2）

> 价值：高/中/低；成本：大/中/小（后端模块级/前端页面级粗粒度）。仅列本章（架构+开源借用+AI 预留）条目；流程类、纯前端类建议分别见 D2/D3 章。

### P0（本章最优先）

| 条目 | 价值×成本 | 一句理由 |
|---|---|---|
| **P0-1 第三方对接适配器层**：integration 模块 + 设备/服务两类标准连接器接口 + Mock 实现同接口可切换（参照阿里模板模型+适配器、微瓴对象模型、JeecgBoot local/cloud-api；zhyq 现状：没有） | 高×中 | 全模拟是 zhyq 最大的架构级空白，此层是接真设备/真支付、补停车门禁模块、以及一切开放能力的共同前置件 |
| **P0-2 统一领域事件最小集**：约 10 个进程内领域事件 + 把「审批过→出账单+锁房源」改造为首个事件消费者，预留 HMAC Webhook 出口（参照海康事件中心、OfficeRnD/Nexudus Webhook、明源流程事件；zhyq 现状：没有） | 高×小 | Spring Event 即可起步，成本极小；却同时解耦现有硬编码联动、承载 D2 全部闭环流程、并且是 AI 挂载点的载体 |
| **P0-3 统一空间树主数据**：空间统一编码，合同/工单/能耗/设备全部挂树引用（参照微瓴 POIID、海康统一资源模型、OpenBlue 空间树；zhyq 现状：部分有——building 有树但各模块不挂） | 高×中 | 一根骨架换来「点房间看全貌」、大屏空间下钻、未来资产模块载体与空间级权限四项收益，是性价比最高的模型改造 |
