# #13 IoT 告警生命周期升级设计 · 待实施（本轮自主）

> 版本 v0.1（2026-07-15）· 批次② P1 · 依赖 #8 规则中心（已做）
> 不碰财务。与 #8 的交互见 §5。

## 1. 目标与非目标

**目标**（ThingsBoard 式）：① 防告警风暴——同一设备同一类型的"活动告警"唯一，重复上报只累加次数/更新最后时间，不刷新行；② 补全状态机中间态（处理中/已恢复/误报）的 API；③ 告警可指派受理人（assignee）；④ 规则可按告警类型匹配（扩展 #8 的 RuleEvaluator）。

**非目标**：不建设备类型码表主数据（`iot_device.category` 仍自由文本）；不做告警聚合分析大盘。

## 2. 现状锚点（探查确认）

- `Alarm`（iot_alarm）字段：deviceId, alarmType, level(Integer), status(Integer), location, content, alarmTime。DDL 状态机注释 `1新建 2已确认 3处理中 4已恢复 5已关闭 6误报`，但 `AlarmController` **只实现 confirm(→2)/close(→5)**，3/4/6 无 API。
- **无唯一约束**（deviceId+alarmType 可无限重复插入，风暴不设防）；**无 assignee 字段**；裸 CRUD 无 Service。
- #8 已让 `AlarmController.add()` 发 `AlarmRaised` → 规则引擎自动建单。

## 3. 表结构（Flyway V23）

`iot_alarm` 加列：
| 列 | 类型 | 说明 |
|---|---|---|
| assignee | varchar(64) NULL | 受理人（占位 system/角色码，#7 后接真实） |
| occur_count | int NOT NULL default 1 | 累计发生次数（重复上报累加） |
| first_time | datetime NULL | 首次发生（回填现有行=alarm_time） |
| last_time | datetime NULL | 最后发生（回填=alarm_time） |
| active | tinyint NULL | 活动标记：1=活动告警；关闭/消解/误报时置 NULL（MySQL 唯一键允许多 NULL，避免已关闭同键行冲突） |

**唯一约束**：`uk_active (device_id, alarm_type, active)` —— 保证一个设备+类型只有一条 active=1 的告警；关闭后 active=NULL 退出唯一域。回填现有行 active=1、first_time=last_time=alarm_time、occur_count=1。

## 4. 组件

- **Alarm 实体**加字段：assignee, occurCount, firstTime, lastTime, active。
- **AlarmService**（新，承载去重+状态机；现无 Service）：
  - `raise(alarm)`：按 (deviceId, alarmType, active=1) 查活动告警——存在则 `occur_count+1`+`last_time=now`（**不发 AlarmRaised**，避免重复建单）；不存在则 insert(active=1, first=last=now, count=1) 并发 `AlarmRaised`（#8 消费建单）。用唯一键兜并发（插冲突则退化为累加）。
  - 状态转换：`confirm(→2)`、`start(→3处理中,可带 assignee)`、`recover(→4已恢复, active=NULL)`、`close(→5, active=NULL)`、`falsePositive(→6误报, active=NULL)`。每步校验合法前驱态。
  - `assign(id, assignee)`：指派受理人。
- **AlarmController** 改造：`add` 改调 `alarmService.raise`（发 AlarmRaised 点随之从 controller 挪进 service）；补 start/recover/falsePositive/assign 端点。保留 confirm/close 语义（仍到 2/5，close 额外置 active=NULL）。
- **RuleEvaluator 扩展**（#8）：condition_json 增加 `alarmType` 精确匹配（event 带 alarmType；需给 AlarmRaised 加 alarmType 字段或在规则侧按告警查——取轻量：给 AlarmRaised record 加 alarmType 字段，发事件时带上）。deviceType 留后续。

## 5. 与 #8 的交互（关键）

- #8 在告警"新建"时发 `AlarmRaised`→建单。#13 的去重让**重复上报更新既有行、不发 AlarmRaised**→不重复建单（双重保险：#8 本身还有 source_alarm_id 去重）。
- 告警 id 不变，故 #8 的 source_alarm_id 去重继续有效。
- 若给 AlarmRaised 加 alarmType 字段，需同步改 #8 的发布点与 RuleEngineListener 的消费（record 加字段是破坏性改动，编译期会提示所有构造点，安全）。

## 6. 零触碰 & 决策

- 零触碰：只加列（含回填）、加 Service/端点；不改既有 confirm/close 对外语义。既有告警查询不受影响（新列可空/有默认）。
- D1 去重键：`active` NULL 化关闭（MySQL 多 NULL 不冲突），避免"已关闭同键多行"唯一冲突。
- D2 受理人：占位（#7 后真实）。
- D3 规则匹配：本轮到 alarmType，deviceType 留后续。
